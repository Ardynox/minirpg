# MiniRPG 文档总览

> 这份索引用来说明每份文档各自负责什么，以及应该先读哪一份。

---

## 推荐阅读顺序

1. [`../minirpg.md`](../minirpg.md)
   项目目标、技术约束、设计原则、默认开发方式。
2. [`../ARCHITECTURE.md`](../ARCHITECTURE.md)
   当前代码实现的职责边界、调用链、分层关系。
3. [`./CODEBASE_MAP.md`](./CODEBASE_MAP.md)
   目录结构、模块依赖、数据流、代码导航。
4. [`./TODO.md`](./TODO.md)
   代码审查遗留问题、技术债和后续收敛项。

## 文档分工

| 文档 | 主要用途 | 什么时候看 | 什么时候更新 |
|------|----------|------------|--------------|
| `minirpg.md` | 项目约定与开发原则 | 设计前、评审前、准备新增模块/实体/框架时 | 约定、非目标、开发原则发生变化时 |
| `ARCHITECTURE.md` | 当前实现事实 | 理解职责边界、调用链、模块归属时 | 模块职责、分层边界、调用链变更时 |
| `Docs/CODEBASE_MAP.md` | 代码导览 | 快速定位目录、依赖关系、数据流时 | 目录结构或主要数据流明显变化时 |
| `Docs/TODO.md` | 审查遗留项 | 判断现有问题、技术债优先级时 | 新发现问题、问题关闭或重分类时 |

## 维护约定

- 约定、原则、非目标写在 `minirpg.md`，不要散落到其他文档。
- 当前代码已经怎样实现，写在 `ARCHITECTURE.md`，不要把“应该怎样”混进去。
- 代码导航和系统地图写在 `Docs/CODEBASE_MAP.md`，不要重复每个类的完整职责说明。
- 审查问题和后续收敛项写在 `Docs/TODO.md`，不要把 TODO 混进架构事实文档。
- 如果一次改动同时改变了“项目约定”和“当前实现边界”，要同步更新对应两份文档。

## 当前建议

- 根目录保留 `minirpg.md` 和 `ARCHITECTURE.md`，避免打断已有引用。
- `Docs/` 目录作为辅助文档区，放索引、代码地图、审查清单和后续补充材料。
