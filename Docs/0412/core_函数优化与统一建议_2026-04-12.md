# Core 函数优化与统一建议（2026-04-12）

## 1. 范围与方法

- 扫描范围：`MiniRPG.Shared/Core/**/*.cs`
- 当前规模：
  - 145 个 C# 文件
  - 31,558 行源码
  - 1,442 个方法签名
- 这份文档不是再做一次职责边界审计，而是回答更务实的问题：
  - 哪些函数簇已经出现重复实现
  - 哪些地方适合抽象、合并、统一
  - 哪些地方暂时不要为了“形式统一”去硬抽象

## 2. 总结论

- 当前 `Core` 最值得做的不是“继续大拆目录”，而是收掉几类已经成型的重复模式。
- 真正有收益的统一点主要集中在 8 类：
  1. 行为链 `TryExecute` 模板统一
  2. 路径搜索 + 移动提交 helper 统一
  3. `ActionExecutionResult / NeedActionResult` 一类结果模型统一
  4. `ActionModule` 的技能 `EffectType` 字符串分发统一
  5. `SaveModule` 的 snapshot mapper 继续拆分
  6. `AppSettingsStore / WorldStore / GameDataLocator` 的文件与路径基础设施统一
  7. `GameEvent` 身份填充 helper 统一
  8. `GameLocalizer` 的静态 switch 与快照循环统一
- 当前不建议做的事情也很明确：
  - 不建议把所有 `Result` 类硬塞进一个超级泛型基类
  - 不建议为了消除所有 `Clone()`/DTO 构造而引入反射 mapper
  - 不建议再把已经拆薄中的 `WorldMap` 重新大范围改名搬家

## 3. 优先级建议

### P1：现在做，收益高、风险可控

1. 统一行为链执行模板
2. 提炼移动/寻路 helper
3. 统一动作结果模型
4. 用注册表替代 `EffectType` 多处字符串分发
5. 拆 `SaveModule` 的 mapper 与通用复制 helper

### P2：接着做，主要改善维护性

6. 提炼 JSON 文件存储基础设施
7. 提炼 `GameEvent` 身份填充 builder/helper
8. 把 `GameLocalizer` 改成表驱动

### P3：暂缓，作为自然演进方向

9. 逐步让新代码绕过 `WorldMap` 兼容 facade，直接用子服务
10. 把 `DebugModule` 命令分发改成注册表

## 4. 重点建议

### 4.1 行为链 `TryExecute` 模板可以统一

当前重复最明显的一组，是 AI 行为链里多个模块的公共模板：

- `MiniRPG.Shared/Core/AI/FireBehaviorModule.cs:13`
- `MiniRPG.Shared/Core/Health/HealthBehaviorModule.cs:10`
- `MiniRPG.Shared/Core/Health/TemperatureBehaviorModule.cs:14`
- `MiniRPG.Shared/Core/Needs/NeedBehaviorModule.cs:43`
- `MiniRPG.Shared/Core/Job/JobBehaviorModule.cs:22`

这些函数现在都长得很像：

- 接口基本一致：`TryExecute(state, actor, perception, tickBuffs, behaviorContext)`
- 先做若干前置短路
- 执行子动作
- 合并 `Events`
- 如果 `Consumed` 再 `actor.TickBuffs()`

重复症状：

- `HealthBehaviorModule.Finalize`：`MiniRPG.Shared/Core/Health/HealthBehaviorModule.cs:61`
- `FireBehaviorModule.Finalize`：`MiniRPG.Shared/Core/AI/FireBehaviorModule.cs:217`
- `NeedBehaviorModule.Finalize`：`MiniRPG.Shared/Core/Needs/NeedBehaviorModule.cs:179`
- `JobBehaviorModule` 虽然没单独抽 `Finalize`，但逻辑相同：`MiniRPG.Shared/Core/Job/JobBehaviorModule.cs:65`

建议做法：

- 新增一个轻量模板，比如 `BehaviorExecution.Run(...)`
- 统一处理：
  - 结果对象创建
  - `Consumed` 合并
  - `Events` 追加
  - `tickBuffs` 收尾
- 每个行为模块只保留本域判断逻辑，不再自己写一遍 `Finalize`

收益：

- 少掉 5 套相同模板代码
- 后续新增行为模块时，接口天然统一
- `AIDispatcher` 更容易改成表驱动行为链

### 4.2 路径搜索 + 提交移动的重复非常多，应该抽 helper

当前多个模块都重复写了同一套路径逻辑：

- `MiniRPG.Shared/Core/AI/FireBehaviorModule.cs:63`
- `MiniRPG.Shared/Core/AI/FireBehaviorModule.cs:92`
- `MiniRPG.Shared/Core/Health/TemperatureBehaviorModule.cs:51`
- `MiniRPG.Shared/Core/Health/TemperatureBehaviorModule.cs:90`
- `MiniRPG.Shared/Core/Needs/NeedBehaviorModule.cs:95`
- `MiniRPG.Shared/Core/Needs/NeedBehaviorModule.cs:115`
- `MiniRPG.Shared/Core/Job/JobExecutor.cs:247`

重复模式基本一致：

1. `Pathfinding.NextStep(...)`
2. 传一个安全判定 lambda
3. 成功后 `ActionModule.TryMove(...)`
4. 再把 `Events` 塞进某个 result
5. 用 `Events.Count > 0` 反推 `Consumed`

这里不只是“代码重复”，还有实际性能问题：

- `TemperatureBehaviorModule.FindNearestCampfire` 和 `FindCoolestCell`
  - 在扫描候选格时反复调用 `Pathfinding.NextStep`
  - 见 `MiniRPG.Shared/Core/Health/TemperatureBehaviorModule.cs:123`、`:156`
- `FireBehaviorModule.FindTargetFireCell` / `FindSaferCell`
  - 在候选循环中也反复做一步寻路
  - 见 `MiniRPG.Shared/Core/AI/FireBehaviorModule.cs:107`、`:172`

建议做法：

- 先提炼一个最小 helper，例如：
  - `BehaviorMove.TryStepToward(...)`
  - `BehaviorMove.TryMoveToward(...)`
- 再视情况继续做第二层：
  - `BehaviorSearch.FindNearestReachableCell(...)`
  - `BehaviorSearch.ScoreReachableCells(...)`

务实建议：

- 第一批先只抽“单次寻路 + 提交移动”
- 第二批再决定要不要做 BFS/评分器，避免第一次就过度抽象

### 4.3 `ActionExecutionResult` 和 `NeedActionResult` 已经完全重复

当前至少有两套结构完全相同的结果模型：

- `MiniRPG.Shared/Core/Combat/SkillCasting.cs:28`
  - `ActionExecutionResult`
- `MiniRPG.Shared/Core/Needs/NeedModels.cs:148`
  - `NeedActionResult`

它们都只有：

- `bool Consumed`
- `List<GameEvent> Events`

这已经不是“语义相近”，而是“形状完全一致”。

建议做法：

- 直接保留一个共享结果模型，例如：
  - `GameActionResult`
  - 或保留 `ActionExecutionResult` 作为共享类型
- `NeedActionResult` 改成别名式迁移，逐步消失

不建议做法：

- 不要把 `FacilityWorkResult`、`TradeResult`、`PartyActionResult` 一股脑并入同一个大基类
- 因为这些结果还带有领域字段，比如 `FailureReason`、`MissingMaterials`、`Facility`

结论：

- 这里适合“收 1 个完全重复类型”
- 不适合“强行统一所有结果类型”

### 4.4 技能 `EffectType` 目前是多处分散的字符串协议，适合收成注册表

当前 `EffectType` 字符串已经散落到多个文件里：

- `MiniRPG.Shared/Core/Combat/ActionModule.cs:236`
- `MiniRPG.Shared/Core/Config/GameLocalizer.cs:195`
- `MiniRPG.Shared/Core/Data/SkillQuery.cs:41`
- `MiniRPG.Shared/Core/AI/SimpleBrain.cs:150`
- `MiniRPG.Shared/Core/Combat/CombatModule.cs:37`

最明显的问题在 `ActionModule.TryCastSkill`：

- `MiniRPG.Shared/Core/Combat/ActionModule.cs:236`
- 这里有一整段 `switch (validation.Skill!.EffectType)`
- 新增一个技能效果时，往往要同步改：
  - `ActionModule`
  - `SkillQuery`
  - `GameLocalizer.LocalizeEffectType`
  - 可能还有 AI 排序/判断逻辑

这说明 `EffectType` 已经不是自由文本，而是隐式枚举。

建议做法：

- 引入 `SkillEffectId` 常量集，先停止裸字符串扩散
- 下一步再把它升级成注册表：
  - handler
  - localization key
  - 目标规则
  - 是否算攻击/是否算工具技能

收益：

- 新增一种 effect 不再需要到处找字符串
- 运行时分发、查询分类、本地化都能挂同一份元数据

### 4.5 `SaveModule` 继续拆 mapper，已经到值得动手的程度

`SaveModule` 现在仍然是 Core 最大热点之一：

- `MiniRPG.Shared/Core/Map/SaveModule.cs:135`
- `MiniRPG.Shared/Core/Map/SaveModule.cs:184`
- `MiniRPG.Shared/Core/Map/SaveModule.cs:510`
- `MiniRPG.Shared/Core/Map/SaveModule.cs:591`

重复/可统一点有三层：

#### 第一层：类型对称映射成对出现

例如：

- `BuildActorSnapshot` / `CreateActor`
- `BuildLimbSnapshot` / `CreateLimb`
- `BuildRaceSnapshot` / `CreateRace`
- `BuildProfessionSnapshot` / `CreateProfession`
- `BuildBuffSnapshot` / `CreateBuff`
- `BuildQuestSnapshot` / `CreateQuest`

这些成对函数已经说明，`SaveModule` 其实在同时承担“存档总控”和“子模型 mapper 集合”。

#### 第二层：泛型工具重复

- `MiniRPG.Shared/Core/Map/SaveModule.cs:1006`
  - `MapList`
- `MiniRPG.Shared/Core/Map/SaveModule.cs:1016`
  - `CopyDictionary`
- `MiniRPG.Shared/Core/Map/ItemSnapshotMapper.cs:227`
  - 同样一份 `MapList`
- `MiniRPG.Shared/Core/Map/ItemSnapshotMapper.cs:235`
  - 同样一份 `CopyDictionary`

这已经可以直接抽成共享 helper 了。

#### 第三层：总流程与 mapper 混在一起

`BuildSnapshot` / `ApplySnapshot` 里混了：

- 预同步
- payload 组装
- dirty chunk 收集
- header/title 构建
- JSON 解析
- 子对象 mapper

建议做法：

- 先只拆 mapper，不动总流程
- 推荐拆法：
  - `ActorSaveMapper`
  - `TimelineSaveMapper`
  - `WeatherSaveMapper`
  - `ChunkSaveMapper`
  - `QuestSaveMapper`
  - `SaveCollectionUtil`（收 `MapList` / `CopyDictionary`）

这样收益最大，风险最可控。

### 4.6 `AppSettingsStore / WorldStore / GameDataLocator` 可以共享基础设施，但不要合并业务

当前这三个文件都在自己处理文件系统与 JSON：

- `MiniRPG.Shared/Core/Config/AppSettingsStore.cs:187`
- `MiniRPG.Shared/Core/Map/WorldStore.cs:195`
- `MiniRPG.Shared/Core/Config/GameDataLocator.cs:21`

可统一的不是业务，而是基础设施：

- 读 JSON
- 写 JSON
- `Directory.CreateDirectory`
- 路径标准化
- 安全路径检查
- 错误吞吐/日志

建议做法：

- 新增小型基础设施 helper，例如：
  - `JsonFileStore`
  - `PathSafety`
  - `UserDataPaths`
- 不要把 `AppSettingsStore` 和 `WorldStore` 合成一个 store

因为它们的业务职责不同：

- `AppSettingsStore` 是全局设置
- `WorldStore` 是世界目录/存档布局/迁移

正确方向是“共享底层读写工具”，不是“共享上层业务类”。

### 4.7 `GameEvent` 身份填充非常重复，适合 builder/helper

当前很多模块在重复写：

- `IdentificationModule.PopulateInitiatorIdentity(...)`
- `IdentificationModule.PopulateTargetIdentity(...)`
- `IdentificationModule.PopulateItemIdentity(...)`

高频文件包括：

- `MiniRPG.Shared/Core/Combat/CombatModule.cs:41`
- `MiniRPG.Shared/Core/Data/InteractionModule.cs:63`
- `MiniRPG.Shared/Core/Health/HealthSystem.cs:200`
- `MiniRPG.Shared/Core/Health/SurgeryModule.cs:181`
- `MiniRPG.Shared/Core/Needs/NeedActionModule.cs:40`

现在的重复主要有两种：

- 先 new `GameEvent(...)`，再手动调用 2~3 个 `Populate*Identity`
- 同类事件在不同系统里字段填充顺序不统一

建议做法：

- 新增轻量 builder/helper，例如：
  - `GameEventFactory.Create(...)`
  - `WithInitiator(...)`
  - `WithTarget(...)`
  - `WithItem(...)`

注意：

- 这里只建议抽“身份填充”和常用字段组合
- 不建议把所有事件构造都塞进一个超大的 EventFactory

### 4.8 `GameLocalizer` 已经很像一份表，但现在还是手写 switch

当前 `GameLocalizer` 有两类重复：

#### 第一类：数据表快照与回写循环重复

- `CaptureBaseSnapshots`：`MiniRPG.Shared/Core/Config/GameLocalizer.cs:24`
- `ApplyPresetTranslations`：`MiniRPG.Shared/Core/Config/GameLocalizer.cs:59`

它们对 item / actor / race / profession / limb / material / category / interaction 都在重复：

- 遍历集合
- 取 base name
- 调 `LocalizeXxx`
- 写回

#### 第二类：本地化 switch 重复

- `LocalizeEquipLayer`：`:162`
- `LocalizeDamageType`：`:171`
- `LocalizeEffectType`：`:195`
- `LocalizeSkillCategory`：`:221`
- `LocalizeTagKey`：`:237`
- `LocalizeFixtureName`：`:252`

建议做法：

- 第一批：
  - 提炼集合级 helper，例如 `CaptureNames` / `ApplyLocalizedNames`
- 第二批：
  - 把若干 switch 改成字典/表驱动
  - 特别是 `EffectType` 本地化应该与 `ActionModule` 的 effect 注册表共享元数据

不建议：

- 不要现在就把所有 `Humanize*` 都做成可配置规则引擎
- 这类 fallback 逻辑还不值得上复杂抽象

### 4.9 `WorldMap` 已经拆成子服务，下一步应该是“减少兼容转发面”

这一轮代码已经在正确方向上前进：

- `MiniRPG.Shared/Core/World/WorldMap.cs:8`
  - 明确变成薄路由层
- 子服务已经拆出：
  - `TerrainAccess`
  - `EntityAccess`
  - `ActorIndex`
  - `FacilityIndex`
  - `WorldQuery`

这意味着：

- 以前那个“大而全 WorldMap”已经开始被收薄
- 下一步不该再大拆目录，而该减少新调用继续走兼容转发

务实建议：

- 保留 `WorldMap` 兼容 facade 给旧调用
- 新代码优先直接依赖子服务
- 尤其在 world 内部函数里，避免再通过 `WorldMap -> 子服务` 来回转发

### 4.10 `DebugModule` 适合命令注册表，但优先级不高

`DebugModule.HandleCommand` 目前是 switch 分发：

- `MiniRPG.Shared/Core/Debug/DebugModule.cs:22`

同时还反复出现：

- `ActorModule.GetPlayer(state)` 判空
- `CreateResult("[debug] no player")`

建议做法：

- 后续如果还会继续加命令，就收成：
  - `Dictionary<string, DebugCommandHandler>`
  - 或至少按 `spawn / weather / facility / session` 拆子处理器

不建议现在就优先做：

- 因为它主要是维护性问题，不是当前最值钱的重复热点

## 5. 分目录结论

### AI

- 重点优化：
  - `AIDispatcher.cs`
  - `FireBehaviorModule.cs`
  - `SimpleBrain.cs`
- 建议：
  - 行为链模板统一
  - effect 类型注册表
  - 行为移动 helper

### Combat

- 重点优化：
  - `ActionModule.cs`
  - `TimelineTurnManager.cs`
- 建议：
  - 技能 effect handler 注册表
  - 玩家 action handler 表驱动
  - 合并通用动作结果模型

### Config

- 重点优化：
  - `AppSettingsStore.cs`
  - `GameLocalizer.cs`
  - `GameDataLocator.cs`
- 建议：
  - 文件/路径基础设施抽离
  - 本地化表驱动

### Data

- 整体较稳。
- 可做的小统一：
  - 若后续继续增加 identity/event 逻辑，优先抽 `GameEvent` builder，不要把重复填充继续分散到 `InteractionModule`、`InventoryModule`、`PartyModule`。

### Debug

- 当前重点是命令注册表，不是结构大改。

### Facility / Farm / Social / Trade / Zone

- 这几块整体函数密度不算高。
- 不建议为了统一而大抽象。
- 如果要动，只建议统一结果模型和事件构造 helper。

### Health / Needs / Job

- 这是最适合做“模板统一 + 移动 helper”的区域。
- 当前重复最明显、收益最高。

### Map

- `SaveModule` 是首要目标。
- `WorldStore` 和 `SaveModuleWeatherAdapter` 说明 Map 侧已经在做基础设施化，这条线适合继续拆 mapper 和共享 util。

### Multiplayer

- 当前主要问题不是函数重复，而是局部偏厚。
- 暂时不建议优先做统一抽象。

### Weather / World

- `WorldMap` 薄化方向是对的。
- `WeatherSystem` 后续如果再拆，优先与 World/Save 的 adapter 边界保持一致，不要回退成直接耦合。

## 6. 不建议现在做的事

### 6.1 不要统一所有 `Result`

理由：

- `ActionExecutionResult` 和 `NeedActionResult` 可以收
- 但 `FacilityWorkResult`、`TradeResult`、`PartyActionResult` 带领域字段，强行统一只会让类型更模糊

### 6.2 不要把所有 snapshot mapping 都改成反射/自动 mapper

理由：

- `SaveModule` 的问题是职责太集中，不是手写映射本身有罪
- 自动 mapper 会降低可读性，也不利于版本兼容

### 6.3 不要为了“彻底统一”去一次性替换全部 `WorldMap` 调用

理由：

- 当前 `WorldMap` 薄 facade 已经在正确方向
- 最稳的策略是“新代码直连子服务，旧代码慢慢迁”

## 7. 推荐重构批次

### 批次 1：统一行为执行模板

- 目标：
  - 收掉 `Health / Fire / Temperature / Need / Job` 的重复 `Finalize`
  - 抽公共 `BehaviorExecution` helper

### 批次 2：统一移动/寻路 helper

- 目标：
  - 抽 `TryMoveToward`
  - 抽候选格 reachability helper

### 批次 3：统一动作结果与 effect 注册表

- 目标：
  - 收掉 `NeedActionResult`
  - 给 `EffectType` 建常量或注册表

### 批次 4：拆 `SaveModule` mapper

- 目标：
  - mapper 分文件
  - 通用 `MapList` / `CopyDictionary` 抽出去

### 批次 5：整理 Config/Store 基础设施

- 目标：
  - `JsonFileStore`
  - `UserDataPaths`
  - `PathSafety`

## 8. 最终结论

- 从“函数级优化、合并、统一”的角度看，当前 Core 不是缺少抽象，而是缺少“收敛重复模式”的小型基础设施。
- 最值钱的动作不是大重构，而是把已经重复 3 次以上的模板统一掉：
  - 行为执行模板
  - 移动/寻路提交
  - 动作结果模型
  - `EffectType` 元数据
  - snapshot mapper 工具
- 如果只做一件事，我建议先做：
  - `Health / Fire / Temperature / Need / Job` 行为链模板统一
- 如果做两件事，再加：
  - `SaveModule` mapper 分拆

这两步投入最稳，回报也最大。
