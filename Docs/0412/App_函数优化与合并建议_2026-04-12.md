# App 函数优化与合并建议（2026-04-12）

## 1. 范围与结论

- 范围：`App/**/*.cs`
- 当前快照：43 个 `.cs` 文件，按统一签名扫描约 585 个方法入口
- 目标：不是再判断“有没有越界”，而是找出 `App` 层函数里哪些已经适合继续抽象、合并、统一模板

结论先说：

- `App` 层绝大多数函数现在已经比早期版本清晰，很多小函数是健康的壳层/协调层，不值得为了“统一”而再抽象。
- 真正值得动的点，集中在少数“重复模板”与“高扇出中心”上。
- 这轮更适合做的是“横向收口”，不是再来一轮大迁移。

## 2. 哪些函数暂时不用动

这部分很重要。全量扫下来，下面这些函数虽然数量不少，但大多数已经够清楚，继续抽象反而会把代码读感变差：

- `App/Main.GameplayInput.cs`
  - 主要是输入翻译和鼠标/滚轮桥接，函数短、分支少，保持直接写法更合适。
- `App/Main.Targeting.cs`
  - 目标 HUD 与目标摘要刷新基本是纯协调函数，没有明显重复模板压力。
- `App/Main.Wiring.cs`
  - 虽然事件订阅很多，但它的职责本来就是 wiring；只需要清理重复 guard，不需要再做“万能注册器”。
- `App/RuntimeUi/SettingsFlowModalInputAdapter.cs`
  - 很标准的 modal 输入适配器，小而稳定。
- `App/RuntimeUi/RuntimeViewCoordinator.cs`
  - 作为视图刷新协调器本身是合理的，问题不在它，而在传入它的部分回调。
- `App/RuntimeUi/MapEditorCoordinator.cs`
  - 这是本轮里比较成功的拆分样板，说明“从 Main partial 中抽专职 coordinator”这条路线是对的。

换句话说，不建议为了“统一风格”去硬抽接口、硬做基类。当前最值钱的是处理真正重复的模式。

## 3. 优先级最高的优化/合并点

## 3.1 `ResourceCatalogEditor` 需要按工作流拆开

位置：

- `App/ResourceCatalogEditor.cs`

现状：

- 单类内同时存在节点绑定、文件对话框、事件订阅、UI 列表刷新、预览区域编辑、切片规划、导入、验证、保存、文件系统扫描。
- 典型函数分组已经很明显：
  - 初始化：`BindNodes`、`BuildFileDialogs`、`ConfigureWidgets`、`WireEvents`
  - UI 刷新：`RefreshUi`、`RefreshLists`、`RefreshEditorFields`、`RefreshPreview`
  - 切片：`RefreshSlicePanel`、`StageSlicesFromSelection`、`BuildSliceCandidates`
  - 导入：`ImportImage`、`ImportFolder`、`BuildTileCandidate`、`BuildAnimationCandidate`
  - 验证与保存：`CollectCatalogValidationErrors`、`ValidateEntry`、`SaveCatalog`
  - 文件系统工具：`ListDirectPngFiles`、`ListDirectDirectories`、`TryConvertToResPath`

建议：

- 至少拆成 4 组：
  - `ResourceCatalogEditorController`
  - `ResourceCatalogPreviewService`
  - `ResourceCatalogImportService`
  - `ResourceCatalogValidationService`
- 切片逻辑如果继续长大，再独立 `ResourceCatalogSlicePlanner`

收益：

- 这是当前整个 `App` 层最明显的“能一次性减负”的位置。
- 拆完之后测试边界、Bug 定位、后续扩功能都会轻很多。

## 3.2 `OnCommand` 应该从“大 switch”收口成命令路由表

位置：

- `App/Main.Command.cs::OnCommand`

现状：

- 一个入口同时处理：
  - 死亡态恢复
  - rest 模式收尾
  - MapEditor 门禁
  - dig 命令归一化
  - settings/fog-map 特判
  - debug panel
  - multiplayer save/load 限制
  - gameplay movement / climb / look / inventory / quest
  - debug slash command

问题不是“太长”而已，而是不同层级的规则混在一起。

建议：

- 至少拆成 4 段：
  - `TryHandlePreCommandState`
  - `TryHandleSystemShortcut`
  - `TryHandleModalOrMapOverlayCommand`
  - `TryHandleGameplayCommand`
- gameplay 命令部分适合用字典或表驱动：
  - `Dictionary<string, Action>` 处理纯本地命令
  - 特例分支只保留 `save/load/newmap/debug`

进一步统一：

- `:quicksave` / `save`
- `:quickload` / `load`
- `:dig_up` / `dig_up`
- `:dig_down` / `dig_down`

这些已经是“同义命令”，可以先做一层标准化，再进路由。

## 3.3 单机限制提示需要统一 helper，不要散在各入口

位置：

- `App/Main.Command.cs`
- `App/Main.MapEditor.cs`
- `App/Main.AutoTest.cs`
- `App/Main.Wiring.cs`

现状：

- `ui.multiplayer.disabled.save`
- `ui.multiplayer.disabled.load`
- `ui.multiplayer.disabled.map_editor`

这三类提示在多个入口重复出现，逻辑形式也完全一致：先判断 `IsMultiplayerSession`，再打一条日志，然后 `return`。

建议：

- 抽一个统一 guard helper，例如：
  - `TryRunSinglePlayerAction(string localizationKey, string fallback, Action action)`
  - 或 `GuardSinglePlayerFeature(SinglePlayerFeature.Save/Load/MapEditor)`

适合统一的入口包括：

- `OnCommand`
- `ToggleMapEditor`
- `HandleMenuMapEditor`
- `_settingsFlow.SaveRequested`
- `_settingsFlow.LoadRequested`
- `_settingsFlow.QuickSaveRequested`
- `_settingsFlow.QuickLoadRequested`
- `_worldManager.LegacySaveRequested`

收益：

- 减少重复文本、减少新入口漏加限制、避免未来文案改动时到处找。

## 3.4 本地化刷新应该做成注册式，而不是继续扩 fan-out

位置：

- `App/Main.Settings.cs::RefreshLocalizedUi`
- `App/Main.Startup.cs::FinalizeReadyState`

现状：

- 这两个函数都在手工点名 `.RefreshTexts()`。
- 一旦新增一个运行时模块，就需要回到这些中心函数继续补线。

目前已经重复的对象包括：

- `_multiplayerHub`
- `_multiplayerRoomPanel`
- `_settingsFlow`
- `_multiplayerHubCoordinator.SetTemplates(...)`

建议：

- 建一个简单的注册表，不用过度设计：
  - `List<Action> _runtimeTextRefreshers`
  - `List<Action> _runtimeReadyRefreshers`
- 或者引入极轻量接口：
  - `IRuntimeTextRefreshable`

可拆成三段，而不是一个总刷函数：

- `RefreshCoreTexts()`
- `RefreshVisiblePanelTexts()`
- `RefreshHudAndRenderTexts()`

这样之后新增 UI 模块时，不必继续把 `Main.Settings.cs` 做成唯一入口。

## 3.5 `MainAppFlowCoordinator` 需要继续横切拆，不然会成为新的 Main

位置：

- `App/RuntimeUi/MainAppFlowCoordinator.cs`

现状：

- 当前已经承担：
  - back to menu / session transition
  - character creation flow
  - blank editor flow
  - world manager open/refresh/delete/clean/load
  - prepared load / recovery dialog / switch confirm
  - settings / layout / map editor entry

这里的问题不是越界，而是“所有流程都往它身上挂”。

建议的下一轮拆分：

- `SessionTransitionCoordinator`
  - `HandleBackToMenu`
  - `PrepareSessionTransition`
  - `CommitPreparedLoadAsync`
- `WorldManagerFlowCoordinator`
  - `OpenWorldManager`
  - `RefreshWorldManagerContents`
  - `HandleWorldManager*`
  - `RequestWorldManagerLoad`
- `CharacterCreationFlowCoordinator`
  - `OpenCharacterCreationDialog`
  - `HandleCharacterCreationConfirmed`
  - `HandleWorldSettingsConfirmed`

不一定要一次拆完，但至少别再继续把新流程往这个类里塞。

## 4. 很适合统一模板的重复模式

## 4.1 会话切换与 busy-stage 模板已经出现重复

位置：

- `App/RuntimeUi/MainAppFlowCoordinator.cs::HandleCharacterCreationConfirmed`
- `App/RuntimeUi/MainAppFlowCoordinator.cs::HandleMenuMapEditor`
- `App/RuntimeUi/MainAppFlowCoordinator.cs::CommitPreparedLoadAsync`
- `App/RuntimeUi/MainAppFlowCoordinator.cs::LoadFromMainMenu`
- `App/RuntimeUi/MainAppFlowCoordinator.cs::LoadFromWorldManager`

现状：

- 多个流程都有相似骨架：
  1. 检查 busy
  2. `BeginBusyOperation`
  3. `ShowBusyOperationStageAsync`
  4. `PrepareSessionTransition`
  5. 执行实际 load/start
  6. finalize
  7. `EndBusyOperation`

建议：

- 抽一个通用 runner，例如：
  - `RunBusySessionTransitionAsync(...)`
  - `RunBusyStagesAsync(BusyLoadStages stages, Func<Task<bool>> action, Action onSuccess)`

这样 `new game`、`blank editor`、`prepared load` 可以共享一个骨架，只保留各自差异。

## 4.2 面板懒加载函数适合做一个统一工厂

位置：

- `App/Main.Panels.cs`

现状：

- `EnsureChestPanel`
- `EnsureDialogPanel`
- `EnsureTradePanel`
- `EnsureQuestPanel`
- `EnsureActorInspectPanel`

这些函数的模板非常像：

1. 已存在则返回
2. `LoadPackedSceneCached`
3. `Instantiate<PanelContainer>`
4. 加到 `TopRow`
5. `LocalizationService.LocalizeTree`
6. 构造 Module
7. `Register`
8. 注册拖拽/Chrome

建议：

- 抽一个“只管懒加载模板”的 helper，例如：
  - `EnsurePanel<TModule>(ref field, string scenePath, Func<PanelContainer, TModule> factory, string dragPath, Action closeAction)`

注意：

- `LimbTargetPanel` 和 `DebugPanel` 特殊性较强，不一定要硬塞进同一个 helper。
- 建议只统一那几种完全同模板的 `PackedScene + Module` 面板。

## 4.3 常见 Toggle/Close 模式也能轻量统一

位置：

- `App/Main.Panels.cs`

现状：

- `ToggleStatusPanel` / `CloseStatusPanel`
- `ToggleSkillBarPanel` / `CloseSkillBarPanel`
- `ToggleSkillManager` / `CloseSkillManagerPanel`
- `ToggleQuestPanel` / `CloseQuestPanel`
- `ToggleInventory` / `CloseInventoryPanel`

它们的模式大多是：

- visible 则 close
- 否则 open/visible=true
- `PushFocus`
- 关闭时 `OnPanelClosed`
- 少数带 `FlushMap` 或刷新

建议：

- 不要抽成“万能面板基类”。
- 只做两个轻 helper 就够了：
  - `ToggleSimplePanel(...)`
  - `ClosePanelIfVisible(...)`

这样既能减少样板代码，也不会把特殊逻辑藏进过度抽象里。

## 4.4 肢体目标请求构造可以统一 builder

位置：

- `App/Main.Skill.cs`

现状：

- `OpenLimbTargetPanel(Actor, skill)`
- `OpenOperationTargetPanel`
- `OpenCorpseHarvest`
- `CreateOperationOption`
- `CreateCorpseHarvestOption`
- `HandleLimbTargetConfirmed`

这里已经不只是“打开面板”，而是开始形成一套 limb-target request 构造规则。

建议：

- 抽一个专门 builder：
  - `LimbTargetRequestBuilder`
- 或先退一步做两个 helper：
  - `BuildActorLimbTargetRequest(...)`
  - `BuildItemLimbTargetRequest(...)`

收益：

- 手术、攻击、尸体采集都能走一致的数据结构。
- 后面如果要加新的 limb-target 技能，不会继续堆在 `Main.Skill.cs`。

## 4.5 时间线动作到多人命令的映射应该独立出去

位置：

- `App/Main.Timeline.cs::TryBuildClientCommand`

现状：

- `TimelinePlayerActionType -> ClientCommand`
  的映射逻辑已经是独立知识点。
- 现在放在 `Main.Timeline.cs` 中，和 watch mode、rest mode、death UI 混在一起。

建议：

- 直接抽成静态 mapper：
  - `TimelineClientCommandMapper.TryMap(action, actorId, out command)`

收益：

- 多人输入、单人 timeline、客户端命令映射三者会更解耦。
- 以后新增 action type 时，映射修改点更单一。

## 5. 需要修正但不要“过抽象”的点

## 5.1 `SyncViewToActiveActor` 不应该继续写 `_state.PlayerX/Y/Z`

位置：

- `App/Main.MapAndCamera.cs::SyncViewToActiveActor`
- `App/RuntimeUi/RuntimeViewCoordinator.cs::FlushMap`

现状：

- 为了让相机和 UI 跟随当前激活角色，直接把 `_state.PlayerX/Y/Z` 改成当前激活角色位置。

这个问题的本质是：

- 视图焦点状态和领域“玩家坐标”状态被混用了。

建议：

- 不建议做大重构，但至少应该改成独立 view anchor：
  - `GetActiveViewAnchor()`
  - 或 `_viewAnchorX/Y/Z`
- `RuntimeViewCoordinator.FlushMap` 用 view anchor 喂给 renderer 即可，不再反写领域状态。

## 5.2 启动装配可以“表驱动”，但不要过度框架化

位置：

- `App/Main.Startup.cs::BindSceneTreeNodes`
- `App/Main.Startup.cs::InitializePanelsAndChrome`
- `App/Main.Startup.cs::InitializeCoordinators`

现状：

- 这三个函数都是合法的 composition root，但节点获取、Theme 赋值、Module 构造的模板已经比较密集。

建议：

- 用小规格数据统一相似初始化，而不是引入复杂 DI：
  - HUD overlay 创建规格
  - overlay panel 创建规格
  - coordinator 装配分组 helper

例如先把这几组抽成局部 helper 即可：

- `CreateOverlayHudModules()`
- `CreateOverlayPanels()`
- `CreateRuntimeCoordinators()`

这样能减读压，但不会把启动流程藏进过深的框架。

## 6. 建议的落地顺序

按性价比排序，我建议这样推进：

1. 先拆 `ResourceCatalogEditor`
2. 再收口 `OnCommand` 与“单机限制 guard”
3. 然后拆 `RefreshLocalizedUi` 的注册式刷新
4. 再继续横切 `MainAppFlowCoordinator`
5. 最后处理面板模板、技能目标 builder、timeline mapper

原因很简单：

- 前三项收益最大，而且直接减少未来改代码时的重复劳动。
- 后三项更偏结构整洁，适合在主流程稳定后推进。

## 7. 最终判断

这轮全量看下来，`App` 层不是“哪里都该重构”，而是已经进入第二阶段：

- 小函数普遍健康
- 中型协调器逐步成型
- 真正的问题集中在少数高扇出中心与重复模板

如果只做一件事，优先拆 `ResourceCatalogEditor`。

如果做一组连续优化，最值得的一条线是：

- 命令路由统一
- 单机 guard 统一
- 文本刷新注册化
- 会话切换 busy 流程模板化

这条线能明显降低 `Main` 与 `MainAppFlowCoordinator` 继续膨胀的速度。
