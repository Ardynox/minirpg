# App 层职责边界全量审计（2026-04-12）

## 1. 审计范围

- 范围：`App/**/*.cs`，包含 `App/RuntimeUi/*` 与 `App/ResourceCatalogEditor.cs`
- 样本：35 个 `.cs` 文件，按签名扫描约 625 个函数/构造入口
- 目标：判断 `App` 层每个函数是否仍处在“应用层/胶水层”职责边界内，而不是重新滑回领域逻辑、基础设施细节或单类过载

本次审计采用“逐函数检查、按函数组汇总”的写法：同一文件内若一组函数承担相同职责，就合并成一个函数组描述；若同一文件里同时存在健康边界和越界残留，会在备注中把具体方法点名。

## 2. 判定标准

### 2.1 `App` 层允许承担的职责

- Godot 场景入口、生命周期、节点装配、事件订阅
- 输入翻译：把键鼠/命令字符串转成应用动作
- 会话编排：开始游戏、继续游戏、切世界、进入编辑器、多人连接
- UI 协调：面板可见性、焦点、HUD 刷新、弹窗切换、日志与特效呈现
- 适配与桥接：把 Core/Module 的结果转成 UI 侧副作用

### 2.2 不应继续堆在 `App` 层的职责

- 直接承载大块领域判定逻辑，尤其是“规则选择 + 状态写入”一起做
- 视图问题通过改写领域状态来解决
- 同一套 view-model/格式化逻辑在 `Main` 和 coordinator 里重复存在
- 已迁移出去但仍保留在入口类中的兼容壳、空实现、抛异常占位
- 单个类同时承担 UI 绑定、预览、导入、验证、持久化、文件系统扫描等 4 类以上职责

### 2.3 评级

- `A`：在职责边界内，职责单一
- `B`：在职责边界内，但已经偏重，继续扩展会很脆
- `C`：边界漂移/迁移残留，建议尽快删除或迁移
- `D`：明显超出单类职责，已构成维护热点

## 3. 总结结论

- 这轮重构是有效的。`App` 层已经不再是“所有逻辑都堆在 `Main.cs`”的旧状态，输入、启动、视图刷新、多人、事件呈现、调试、天气实验室都已经出现独立 coordinator / controller。
- 大多数运行时函数目前仍在应用层边界内，尤其是 `RuntimeUi` 目录下的大部分文件，职责定义是清晰的。
- 现在最主要的问题不再是“没有边界”，而是“少数热点文件里仍有残留函数、重复函数和超大职责面”。

当前最值得优先处理的 6 个热点：

1. `App/ResourceCatalogEditor.cs` 仍是明显的单类过载，属于 `D` 级热点。
2. `App/Main.cs` 里还留着一组迁移残骸：`DoLoad`、`LogLoadFailure`、`BuildLoadFailureMessage`、`SetWorldManagerStatus`、`ClearWorldManagerStatus`、`SaveCurrentSessionAndLoadFromWorldManager`、`OpenSwitchConfirmation`。
3. `App/Main.Multiplayer.cs` 里仍保留一组已被 `MultiplayerHubCoordinator` 接管的重复 helper：`BuildMultiplayerRoomPlayerOptions`、`BuildMultiplayerRoomActorOptions`、`BuildMultiplayerRoomPlayerLabel`、`BuildMultiplayerRoomActorLabel`、`DescribeMultiplayerHostMode`、`IsAssignableMultiplayerRoomActor`、`GetAssignableMultiplayerActorPriority`。
4. `App/Main.Command.cs::OnCommand` 仍然过重，既做命令表又做权限/模式判断，还直接触发多个流程。
5. `App/Main.Settings.cs::RefreshLocalizedUi` 和 `App/RuntimeUi/MainAppFlowCoordinator.cs` 仍然是高扇出协调中心。
6. `App/Main.MapAndCamera.cs::SyncViewToActiveActor` 用修改 `_state.PlayerX/Y/Z` 的方式驱动视图，是典型的“视图问题改领域状态”。

## 5. 具体热点与建议

### 5.1 `Main.cs` 里不该继续保留的迁移残留

以下函数已经不再适合作为 `Main` 的长期职责：

- `DoLoad`
- `LogLoadFailure`
- `BuildLoadFailureMessage`
- `SetWorldManagerStatus`
- `ClearWorldManagerStatus`
- `SaveCurrentSessionAndLoadFromWorldManager`
- `OpenSwitchConfirmation`

原因：

- 同名能力已经被 `MainAppFlowCoordinator` 接管
- 这些方法不是空壳就是旧流程残留
- `OpenSwitchConfirmation` 直接抛异常，说明入口类里仍残留“过渡接口”

建议：

- 若无调用，直接删除
- 若仍需要兼容回调，改成纯转发并在一轮内清理调用点

### 5.2 `Main.Multiplayer.cs` 的重复 helper 应归一

以下 7 个函数已经与 `MultiplayerHubCoordinator` 重复：

- `BuildMultiplayerRoomPlayerOptions`
- `BuildMultiplayerRoomActorOptions`
- `BuildMultiplayerRoomPlayerLabel`
- `BuildMultiplayerRoomActorLabel`
- `DescribeMultiplayerHostMode`
- `IsAssignableMultiplayerRoomActor`
- `GetAssignableMultiplayerActorPriority`

这类函数已经不应再停留在 `Main` partial 中，因为它们本质是多人房间 UI 的 view-model 计算。

### 5.3 `OnCommand` 应拆成表驱动 command router

`Main.Command.cs::OnCommand` 当前同时承担：

- 死亡态返回菜单
- 休息模式打断
- 模式门禁（地图编辑 / 设置 / fog map / timeline lock）
- 单机/多人限制提示
- 命令到函数调用的总路由

它仍然处在应用层边界内，但容量已经过大。建议后续拆成：

- `SystemCommandRouter`
- `GameplayCommandRouter`
- `ModalCommandPolicy`

### 5.4 `RefreshLocalizedUi` 仍然是全局扇出点

`Main.Settings.cs::RefreshLocalizedUi` 一次性触达：

- 菜单/多人/设置
- 世界管理/建角/恢复对话框
- 地图编辑条
- 多个 HUD
- 所有可见面板
- 日志与地图刷新

这类函数短期内还能工作，但每增加一个新 UI 模块都要继续往这里接线。建议把“本地化刷新”拆成：

- 永久注册模块列表
- 面板刷新列表
- 渲染/HUD 刷新列表

### 5.5 `MainAppFlowCoordinator` 该继续横切拆分

它现在已经比旧 `Main` 好很多，但仍然过宽。最合理的下一步不是继续往里塞逻辑，而是拆成：

- `SessionFlowCoordinator`
- `WorldManagerFlowCoordinator`
- `PreparedLoadCoordinator`

拆分目标不是减少行数，而是让“继续游戏 / 世界管理 / 载入恢复 / 切换确认”四条子流程分别有独立演进边界。

### 5.6 `ResourceCatalogEditor` 不是层级越界，而是类内职责越界

`ResourceCatalogEditor` 并没有跑到 Core 去做事情，它的问题是一个类里塞了太多不同种类的事情：

- 节点绑定与 UI 事件
- 列表/属性/预览刷新
- 裁切候选生成
- 导入图片/目录
- ID、Tag、Category 规则
- Catalog 验证与保存
- 文件系统扫描与路径转换

建议最少拆成这 5 块：

- `ResourceCatalogEditorController`
- `ResourceCatalogPreviewService`
- `ResourceCatalogSlicePlanner`
- `ResourceCatalogImportService`
- `ResourceCatalogValidationService`

## 6. 建议的后续重构顺序

1. 删除 `Main.cs` 与 `Main.Multiplayer.cs` 中的残留/重复函数，先做“减法”。
2. 把 `OnCommand` 改成表驱动路由，不再让一个函数承载所有命令门禁。
3. 把 `MainAppFlowCoordinator` 拆成 `SessionFlow` 与 `WorldManagerFlow` 两块。
4. 给视图引入独立 camera/view anchor，替代 `SyncViewToActiveActor` 对 `_state.PlayerX/Y/Z` 的写入。
5. 单独重构 `ResourceCatalogEditor`，因为它已经是独立工具，不需要受运行时主流程节奏限制。

## 7. 最终判断

如果只看“App 层是否完全失控”，答案是否定的：当前 `App` 层已经形成了比较清晰的应用层边界，尤其是 `RuntimeUi` 下的大部分 coordinator/controller 都是健康的。

如果看“是否还有必须继续收口的边界问题”，答案也是肯定的：问题已经收缩到少数明确热点，而不是全层普遍越界。下一轮最值钱的工作不是再大规模重写，而是继续做三件事：

- 清掉迁移残留
- 拆掉少数高扇出中心
- 把工具型超载类从单类过载状态中解开
