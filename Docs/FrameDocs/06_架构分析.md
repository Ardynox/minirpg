# 06 架构分析

## 分层结构

从前五份文档可以清楚看出当前运行时是三层叠在一个集中入口上的结构：

- `App/Main.cs` 站在最上层，既是组合根，又直接承担输入路由、事件路由、UI 状态机与渲染协调。
- `Module/*` 形成 UI 与流程层，负责面板、菜单、设置流、世界浏览器、渲染与 HUD。
- `Core/*` 是领域与基础设施层，持有 `GameState`、世界块、生成器、存档、回合系统、AI、健康与需求系统。

这一点可以直接回看 [README.md](./README.md) 的分层图、[01_接口文档_入口与UI.md](./01_接口文档_入口与UI.md) 的入口表，以及 [02_接口文档_Core基础与世界.md](./02_接口文档_Core基础与世界.md) / [03_接口文档_Core玩法与系统.md](./03_接口文档_Core玩法与系统.md) 的行为型系统表。

## 核心中枢

当前运行时有四个明确中枢：

- `Main`：负责装配、输入、事件分发、面板协调与刷新收口。它是事实上的应用服务层，但以 Godot 场景脚本形式存在。
- `GameState`：单一运行时事实源。世界、角色、设施、天气、需求、健康、时间线、识别状态都挂在这里。
- `TimelineTurnManager`：唯一负责“谁现在行动、世界何时推进、自动步进何时继续”的回合中心。
- `GameSessionModule`：会话切换中心，负责新游戏、切世界、继续游戏、世界角色存档与楼层切换。

`TileMapRenderModule` 也具有明显中枢性质，但它更偏向“渲染收口中心”，而不是全局流程中枢。相关证据见 [04_调用文档.md](./04_调用文档.md) 的“玩家回合”“AI 回合”“会话 / 世界 / 存档”“视野与渲染”章节，以及 [05_调用链文档.md](./05_调用链文档.md) 的第 3、4、6、7 条链路。

## 稳定边界

系统里已经存在几条比较稳定、值得保留的边界：

- `IGameUI`：把 `DialogUIModule`、`TradeUIModule`、`CombatUIModule` 对 `Main` 的能力诉求收敛成少量动作，说明 UI 子模块并不一定要直接知道 `Main` 的内部结构。
- `IPanel`：把焦点、键盘命令、脏刷新统一成面板协议，`PanelManager` 因而能独立运作。
- `IAnimatable`：让渲染实现不绑定在具体 Spine 或 Tile 节点上。
- `IMapGenerator`、`IViewMode`、`IChunkSimulator`、`IBrainModule`：这些接口表明世界生成、视图模式、chunk 模拟、AI 脑模块都已经被识别成扩展点。

这些边界在 [01_接口文档_入口与UI.md](./01_接口文档_入口与UI.md) 的“重点协作接口”和 [02_接口文档_Core基础与世界.md](./02_接口文档_Core基础与世界.md) / [03_接口文档_Core玩法与系统.md](./03_接口文档_Core玩法与系统.md) 的接口条目中都能直接回链。

## 耦合热点

最明显的耦合热点有四个。

- `App/Main.cs` 过重。它同时承担组合根、输入路由、事件路由、UI 状态机、面板编排、会话切换、渲染协调、调试命令入口。任何新玩法或新 UI 流程，最后几乎都要回到 `Main` 接线。
- `Main.Dispatch` 是跨层汇聚点。`GameEvent` 在这里被翻译成日志、动画、当前目标、高亮、对话 UI、交易 UI、死亡处理等，导致领域事件对表现层的耦合集中在一个巨大 switch 中。
- `GameState` 虽然是单一事实源，但几乎所有静态系统都能直接读写它，带来极高的隐式共享可变状态。
- 大量 `static Module` 与 `static System` 使调用路径直接，但也让替换实现、局部测试和依赖注入的成本升高。

这些热点在 [04_调用文档.md](./04_调用文档.md) 的所有主流程章节中都能反复看到，尤其是“玩家回合”“AI 回合”“会话 / 世界 / 存档”“视野与渲染”。

## 反向依赖

当前最明确的反向层依赖是：

- `Core.Debug.DebugModule -> Module.GameSessionModule`

`DebugModule.HandleCommand` 直接接收 `GameSessionModule session`，并调用 `session.ChangeFloor`、`session.ExportPresetScenario`。这意味着本该位于 Core 内的调试逻辑，已经知道 UI / 会话层的具体实现对象，破坏了 `Module -> Core` 的单向依赖预期。

这一点既能在 [03_接口文档_Core玩法与系统.md](./03_接口文档_Core玩法与系统.md) 的 `DebugModule` 条目中看到，也能在 [04_调用文档.md](./04_调用文档.md) 的“调试命令”章节里看到完整调用关系。

## 扩展点

现有架构已经暴露出一批可落地扩展点：

- 世界生成：`IMapGenerator`，可继续新增生成算法而不动 `GameSessionModule`。
- 视图模式：`IViewMode`，可扩展单层、多层之外的渲染策略。
- AI：`IBrainModule`，已支持通过 `BrainId` 分发不同脑模块。
- 动画：`IAnimatable`，可替换底层动画实现。
- 设置 / 面板焦点：`ISettingsOverlay`、`IPauseMenuOverlay`、`ISettingsFlowFocusHost`、`IPanel`，适合继续做流程拆分。
- 对话 / 交易规则：`DialogRuleEngine`、`TradeModule` 已经与 UI 分开，可以在不改面板的情况下替换规则。

问题不在于“没有扩展点”，而在于扩展点的装配与调度仍高度集中在 `Main`。

## 重构优先级

### P1: 拆 `Main`

优先把 `Main` 中至少三类职责拆出去：

- 启动与装配：形成独立 bootstrap / composition service。
- 输入与命令路由：形成 application command router。
- 事件到 UI 副作用的翻译：把 `Dispatch` 拆成独立的 event presenter / event bridge。

这样做的收益最大，因为它能同时降低入口复杂度和跨层汇聚度。参考 [01_接口文档_入口与UI.md](./01_接口文档_入口与UI.md) 的 `Main` 条目、[04_调用文档.md](./04_调用文档.md) 的全部章节，以及 [05_调用链文档.md](./05_调用链文档.md) 的 1、3、5、7、8 号链路。

### P2: 收紧 `GameState` 读写边界

建议把最容易出错的写路径先封成应用服务或领域门面：

- 会话切换与存档恢复
- 玩家动作提交
- AI 单步推进
- 需求 / 健康同步

目标不是放弃 `GameState`，而是减少“任意静态函数随手改全局状态”的情况。

### P3: 把 `Main.Dispatch` 从 switch 改为事件呈现流水线

可考虑把 `GameEvent` 的 UI 翻译拆成若干 handler：

- 日志 handler
- 动画 / 特效 handler
- 目标与 HUD handler
- 交互分流 handler
- 死亡 / 结束态 handler

这样可以减少 `Main` 的知识密度，也更容易为新事件类型做增量扩展。

### P4: 反转调试依赖

把 `DebugModule` 对 `GameSessionModule` 的依赖改成更薄的接口，例如：

- `IDebugSessionActions.ChangeFloor`
- `IDebugSessionActions.ExportPresetScenario`

或者直接把调试入口提升到应用层，再由应用层调用 `Core` 和 `Module`。

### P5: 降低 static 系统的替换成本

`ActionModule`、`MapModule`、`SaveModule`、`TradeModule`、`HealthSystem`、`NeedSystem` 这类全静态系统短期不会消失，但可以逐步做到：

- 把配置、随机源、文件系统、日志等外部依赖从静态内部拿出去；
- 先让外部依赖可传入，再考虑实例化。

## 总结

当前架构不是“没有边界”，而是“边界存在，但调度权过度集中在 `Main` 上”。因此最有效的方向不是重写所有 Core 系统，而是先削减 `Main` 的跨层指挥职责，保留现有 `GameState + TimelineTurnManager + GameSessionModule + TileMapRenderModule` 这些已经稳定成形的中枢与边界。
