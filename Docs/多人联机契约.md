# MiniRPG 多人联机契约

这份文档只回答一个问题：**客户端的一个操作，从输入到屏幕表现，会走哪几条路？单机、联机、预测三种情况下各自的权威在哪？**

不展开 ENet 协议或房间匹配细节。代码入口请看 [`架构现状.md`](./架构现状.md)。

## 三条提交路径

所有玩家操作最终都归到 `ClientCommand`，由 `App/RuntimeUi/ClientCommandRouter` 统一路由：

| 路径 | 触发方式 | 权威执行者 | 本地是否立即变化 |
| --- | --- | --- | --- |
| 单机直发 | 非多人会话，任何 `ClientCommand` | `LocalSessionBackend.SubmitCommandAsync` → `ServerActionGateway.Execute(_state, command)` | 是，同步 |
| 多人权威 | 多人会话下的非预测命令 | 远端：`MultiplayerSessionBackend.SubmitCommandAsync` → 服务器 → snapshot/delta 回传 | 否，等权威 |
| 多人预测 | 多人会话下的 `MoveClientCommand`（`TrySubmitPredictedMove`） | 本地先改 `_state.PlayerX/Y` 并渲染；命令仍发权威，权威回执触发对账 | 是，乐观 |

## 单机直发

- 入口：`ClientCommandRouter.Submit(command)`，若 `MultiplayerRuntimeCoordinator.TrySubmitClientCommand` 返回 false，则落到 `_sessionBackend.SubmitCommandAsync`。
- 服务端逻辑是 `MiniRPG.Shared.Module.ServerActionGateway.Execute`，**同时**是多人服务器上跑的那一份。这是单机和联机行为一致的根本保证。
- 事件通过 `LocalSessionBackend.DeltaReceived` 立即派发，UI 和 `GameEventPresentationRouter` 同步更新。

## 多人权威

- 入口相同：`ClientCommandRouter.Submit(command)`。多人会话下 `MultiplayerRuntimeCoordinator.TrySubmitClientCommand` 返回 true，命令转到 `_backend.SubmitCommandAsync(command)`。
- 权威执行在服务端（`MiniRPG.Server` 项目）。客户端只收：
  - `SnapshotReceived`（`RoomSnapshotMessage`）：完整 `GameState` 覆盖。
  - `DeltaReceived`（`GameSessionDeltaEnvelope`）：一批 `GameEvent` 增量。
- 命令失败时服务端发 `command_rejected`，`MultiplayerSessionBackend.CommandRejected` 投递失败原因到日志。

## 多人预测（目前仅限移动）

预测只覆盖 `MoveClientCommand`，由 `MultiplayerRuntimeCoordinator.TrySubmitPredictedMove` 处理：

1. **下单**：在 `ClientPredictionState` 里记录 `PredictedMove { requestId, clientTick, dx, dy, predictedX, predictedY, predictedZ }`。
2. **本地立即生效**：`_state.PlayerX/Y += dx/dy`。
3. **渲染乐观动画**：`_presentPredictedActorMotion(new ActorMotionPresentationRequest(..., Blocking: true))`。
4. **发权威**：同一条 `MoveClientCommand` 异步提交给服务端。
5. **对账**：收到 snapshot 时，`ApplyPredictionReconciliation(authoritativeRequestId)` 比较 `预测队列的末端累积` 与服务端返回的 `Authoritative(X,Y,Z)`：
   - Manhattan 距离 ≤ `PredictionConfig.RollbackThresholdManhattan` → `InTolerance`，把预测值作为真值沿用。
   - 超阈值 → `WithRollback`，落权威值并 `_resetActorMotionState()`，日志里记一行 `[Prediction] rollback ...`。
6. **清理**：被服务端 ACK 的预测项通过 `PruneThrough(clientTick)` 从队列移除；超长（> `PredictionConfig.MaxPendingCommands`）的老预测会被 `TrimHistory` 丢弃。

## 状态所有权速查

| 对象 | 权威在 | 客户端只能 |
| --- | --- | --- |
| `GameState.Actors` / `WorldMap` / `Room` | 服务端（多人） / 本地 `ServerActionGateway`（单机） | 乐观预测 `_state.PlayerX/Y`，其余由 snapshot / delta 覆盖 |
| `_state.PlayerX` / `PlayerY` | 权威；客户端通过预测短暂持有 | 预测 + 对账 |
| 渲染状态（`ActorMotionTracker` 等） | 客户端专属 | 本地维护，不要镜像到 `GameState` |
| 选中 / 面板焦点 / 自动寻路 | 客户端专属 | 同上 |
| 存档 | 单机：客户端；多人：由服务端生成 snapshot，客户端只落盘 | 不要客户端主动写服务端场景的存档 |

## 不做什么

- **不要**在多人会话下本地直接修改非 `PlayerX/PlayerY` 的 `GameState` 字段。任何其他字段都应等权威 snapshot / delta。
- **不要**在非 `MoveClientCommand` 上加预测。先让 `ClientPredictionState` 支持命令类型再谈。
- **不要**绕过 `ClientCommandRouter` 直接调 `backend.SubmitCommandAsync`。路由决定"单机/多人/预测"走哪条。
- **不要**假设 `LocalSessionBackend` 的立即同步语义在多人也有效。UI 动画如果依赖"提交完就看得到结果"，多人会穿帮。

## 加新命令的清单题

1. 这条命令的服务器权威是否跑 `ServerActionGateway.Execute`？是的话只需要在客户端入口加路由即可。
2. 是否需要多人预测？默认**不需要**；需要的话参考 `TrySubmitPredictedMove`，并在 `ClientPredictionState` 里加命令类型的对账逻辑。
3. 命令失败要不要提示？`_backend.CommandRejected` 默认写日志，如要走面板提示应挂在 `MultiplayerRuntimeCoordinator` 或 `GameEventPresentationRouter` 上。
4. 是否涉及玩家本地状态快照？是的话要在 `FinalizeLoadedGame` 对齐读档路径。
