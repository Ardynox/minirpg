# MiniRPG 产品愿景

这份文档回答一个稳定问题：**我们到底在做什么游戏？**
当改动方向或新功能评估需要一个"北极星"时，来这里对照。

## 产品定位

- **高自由度、高真实感的单人生存沙盒 RPG**，表现形式为等距 2.5D。
- 设计参考坐标：
  - **Elin**：沙盒深度、物品/技能/角色系统的多重叠加。
  - **僵尸毁灭工程（Project Zomboid）**：硬核生存模拟、需求压力、世界危险、玩家生活即玩法。
  - **RimWorld**：涌现叙事、系统互锁、可追溯结果。
- **玩法即代入感本身**：玩家不追求"通关"，而是在这个世界"生活下去"——吃喝、睡眠、建造、防御、社交、受伤、康复、死亡。
- 目标是让玩家体会到"这是一个真实运转的世界"，而不是"一个布景化的关卡"。

## 核心体验目标

1. **代入感重于爽感**
   玩家感到"我在这个世界里生活、决策、承担后果"，而不是"我在通过一个关卡"。
2. **世界连续运转**
   NPC 有自己的生活轨迹；时间、天气、光照、chunk、需求、情绪在玩家不看的时候也继续演算。存档、继续游戏、多人会话都要维持这种"世界不会因为我关掉游戏而消失"的感觉。
3. **结果可追溯**
   任何操作都有物理、生理或社会层面的具体后果；玩家能从后续表现回推刚才发生了什么。伤害要看肢体，休息要看 bedroll 与周围威胁，吃的东西要有来源，社交会影响关系。

## 玩家控制模型：多角色 + 单焦点

- 玩家不只操控一个角色，而是一支队伍（对应 `MiniRPG.Shared/Core/Data/PartyModule`）。
- **任何时刻只能主动控制队伍里的一个成员**（焦点角色 / `ActiveId`）；其他成员走 AI（`BrainId`）自主生活。
- 队伍可以招募（`PartyModule.TryRecruit`）与解散（`TryDismiss`），但队长不能被解散。
- UI / 输入只作用于焦点角色；切换焦点走 `CycleActive`（Tab 键等）或 `TrySetActive`（点头像）。

## 死亡与复活

**死亡不是终局**。设计方向对齐愿景"结果可追溯 + 世界连续"：

- **焦点角色死亡 → 自动切换**到队伍里下一个活着的成员（`PartyModule.TryPromoteNextLivingMember`）；玩家视角无缝接过去。
- **全队死亡才进入"全灭"流程**（`PartyModule.AnyMemberAlive` 返回 false 时），此时走类似 PZ 永久死的收尾。
- **尸体保留原角色身份**：`ItemCorpseMetadata.SourceActorId` 让复活系统能精确找回是哪个原角色。
- **复活手段可以是科技或魔法**（或神迹），统一接 `MiniRPG.Shared/Core/Revival/ReviveService.TryRevive`；具体方法由上层技能 / 设施配置：
  - 魔法路径：复活法术 skill、复活祭坛 facility、特殊神器 item。
  - 科技路径：克隆舱 facility、纳米修复 item、能量 station。
  - 神迹路径：罕见、概率低但代价小。
- **复活必有代价**——这是愿景里"结果可追溯"的硬要求：
  - 被复活者：挂长期负面 thought（例如 720 回合的 "revived_memory" / mood -8）。
  - 复活者：获得短期正向 thought（例如 240 回合的 "revived_ally" / mood +4）。
  - 材料消耗与成功率由具体 method 配置（尚未落地）。
- **多次复活可累加负面效果**（性格偏移、技能折损、灵魂残缺），给"真的回不来的线"留空间。默认阈值由 `Core/Revival/RevivalCostModel` 给出：每次复活后 mood 负 thought 更重、capacity 折损 +5%（上限 40%），累计 6 次触发 `IsPermanentlyLost`——上层应拒绝复活，让玩家彻底失去这个角色。
- **世界连续性守门**：即使玩家能复活，NPC / Storyteller 依然应该"记得他死过"——这点靠 Thought / MemoryLedger（B3）保障，不是复活机制内部的事。

### 仪式感要求

代价不是纯数字就够——必须被玩家**感受到**。接入 UI 时至少满足：

1. **焦点死亡切换的演出**：屏幕瞬间减饱和（或慢镜头）+ 日志大字"XXX 倒下了" + 镜头缓动切到下一焦点。禁止瞬切，禁止静默。
2. **复活施法/设施需要时间**：魔法路径至少若干回合施法 + 法阵动画；科技路径至少若干回合克隆仓工作。一键即时复活破代入感。
3. **旁观反应**：其他队员 / 附近 NPC 在死亡和复活的那一刻要各获得一条 thought（通过 `Memory / Opinion` 系统），让"这个时刻别人也记得"成为世界连续性的一部分。
4. **复活失败后果可见**：`ReviveService.TryRevive` 失败时（包括 `IsPermanentlyLost` 阈值），不能只 "ok=false" 沉默返回——必须给玩家看到具体失败文本 + 可能的产出（如"残魂"物品、永久损坏的灵魂石）。

这四条是"死亡-复活"被接入具体技能 / 设施 / UI 时的验收条目；不满足其中任何一条，就认为该次接入**没完成**。

## 决策标尺

评估一个改动时，按顺序问自己：

0. **（一票否决）这个改动离"最终可玩"更近了吗？**
   ——在当前仍是早期原型阶段，任何不能把"玩家能连续玩下去的最小闭环"向前推进的改动都应延后。
   技术上再优雅、理论上再符合愿景的系统，只要对玩家闭环没贡献，就不是当下该先做的。
   这条是前置闸门；过了它，再看下面 1–4 条。
1. **这个改动让世界更连续了吗？**
   ——例如 NPC 离开视野后行为是否一致、存档恢复后状态是否完整。
2. **这个改动让系统之间更互锁了吗？**
   ——新机制应该与至少一个已有系统（需求/健康/威胁/性格/天气/时间/社交…）产生可观察的因果关系。
3. **这个改动让玩家的操作后果更可追溯了吗？**
   ——玩家应能从后续 UI、日志、NPC 行为或世界状态读出刚才做过什么。
4. **这个改动保护了"单人优先 + 等距 2.5D"的边界吗？**
   ——不为了 MMO 规模或 3D 写实画面牺牲现有表现风格与会话模型。

前三条都不中的改动通常不是这个项目该优先做的；第 4 条是边界守门，不是加分项。
**第 0 条是前置闸门**：无论后四条怎么亮，没过第 0 条就先不做。

## 明确的非目标

- 不追极端写实画面或 AAA 视觉规模；等距 2.5D 的风格化表现足够。
- 不追 MMO 级的并发与社交规模；多人是"小团体共玩一个世界"而不是大区服。
- 不追无脑数值堆砌或简单数值曲线；深度来自系统互锁，不来自膨胀的伤害与等级。
- 不把"故事"写成固定剧本；故事是玩家自己用系统涌现出来的轨迹。
- 不引入 ECS / 通用状态机 / 总线框架来替代现有运行时结构，当前重构路线优先于框架化（见 [`开发约定.md`](./开发约定.md) 与 [`重构路线图.md`](./重构路线图.md)）。

## 什么时候更新这份文档

只有当产品定位、体验目标或非目标发生变化时才更新。
"又想到一个想做的功能"不是更新这份文档的理由，那应该落到具体系统的设计/重构计划里。
