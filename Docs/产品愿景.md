# MiniRPG 产品愿景

这份文档回答一个稳定问题：**我们到底在做什么游戏？**
当改动方向或新功能评估需要一个"北极星"时，来这里对照。

## 产品定位

- **高自由度、高真实感的单人生存沙盒 RPG**，表现形式为等距 2.5D。
- 设计参考坐标：
  - **Elin**：沙盒深度、物品/技能/角色系统的多重叠加。
  - **僵尸毁灭工程（Project Zomboid）**：硬核生存模拟、需求压力、世界危险、玩家生活即玩法。
  - **RimWorld**：涌现叙事、系统互锁、可追溯结果。
- **玩法即代入感本身**：玩家不追求"通关"，而是在这个世界"生活下去"——吃喝、睡眠、建造、防御、社交、受伤、康复、死亡。
- 目标是让玩家体会到"这是一个真实运转的世界"，而不是"一个布景化的关卡"。

## 核心体验目标

1. **代入感重于爽感**
   玩家感到"我在这个世界里生活、决策、承担后果"，而不是"我在通过一个关卡"。
2. **世界连续运转**
   NPC 有自己的生活轨迹；时间、天气、光照、chunk、需求、情绪在玩家不看的时候也继续演算。存档、继续游戏、多人会话都要维持这种"世界不会因为我关掉游戏而消失"的感觉。
3. **结果可追溯**
   任何操作都有物理、生理或社会层面的具体后果；玩家能从后续表现回推刚才发生了什么。伤害要看肢体，休息要看 bedroll 与周围威胁，吃的东西要有来源，社交会影响关系。

## 玩家控制模型：多角色 + 单焦点

- 玩家不只操控一个角色，而是一支队伍（对应 `MiniRPG.Shared/Core/Data/PartyModule`）。
- **任何时刻只能主动控制队伍里的一个成员**（焦点角色 / `ActiveId`）；其他成员走 AI（`BrainId`）自主生活。
- 队伍可以招募（`PartyModule.TryRecruit`）与解散（`TryDismiss`），但队长不能被解散。
- UI / 输入只作用于焦点角色；切换焦点走 `CycleActive`（Tab 键等）或 `TrySetActive`（点头像）。

## 死亡与复活

**死亡不是终局**。设计方向对齐愿景"结果可追溯 + 世界连续"：

- **焦点角色死亡 → 自动切换**到队伍里下一个活着的成员（`PartyModule.TryPromoteNextLivingMember`）；玩家视角无缝接过去。
- **全队死亡才进入"全灭"流程**（`PartyModule.AnyMemberAlive` 返回 false 时），此时走类似 PZ 永久死的收尾。
- **尸体保留原角色身份**：`ItemCorpseMetadata.SourceActorId` 让复活系统能精确找回是哪个原角色。
- **复活手段可以是科技或魔法**（或神迹），统一接 `MiniRPG.Shared/Core/Revival/ReviveService.TryRevive`；具体方法由上层技能 / 设施配置：
  - 魔法路径：复活法术 skill、复活祭坛 facility、特殊神器 item。
  - 科技路径：克隆舱 facility、纳米修复 item、能量 station。
  - 神迹路径：罕见、概率低但代价小。
- **复活必有代价**——这是愿景里"结果可追溯"的硬要求：
  - 被复活者：挂长期负面 thought（例如 720 回合的 "revived_memory" / mood -8）。
  - 复活者：获得短期正向 thought（例如 240 回合的 "revived_ally" / mood +4）。
  - 材料消耗与成功率由具体 method 配置（尚未落地）。
- **多次复活可累加负面效果**（性格偏移、技能折损、灵魂残缺），给"真的回不来的线"留空间。默认阈值由 `Core/Revival/RevivalCostModel` 给出：每次复活后 mood 负 thought 更重、capacity 折损 +5%（上限 40%），累计 6 次触发 `IsPermanentlyLost`——上层应拒绝复活，让玩家彻底失去这个角色。
- **世界连续性守门**：即使玩家能复活，NPC / Storyteller 依然应该"记得他死过"——这点靠 Thought / MemoryLedger（B3）保障，不是复活机制内部的事。

### 仪式感要求

代价不是纯数字就够——必须被玩家**感受到**。接入 UI 时至少满足：

1. **焦点死亡切换的演出**：屏幕瞬间减饱和（或慢镜头）+ 日志大字"XXX 倒下了" + 镜头缓动切到下一焦点。禁止瞬切，禁止静默。
2. **复活施法/设施需要时间**：魔法路径至少若干回合施法 + 法阵动画；科技路径至少若干回合克隆仓工作。一键即时复活破代入感。
3. **旁观反应**：其他队员 / 附近 NPC 在死亡和复活的那一刻要各获得一条 thought（通过 `Memory / Opinion` 系统），让"这个时刻别人也记得"成为世界连续性的一部分。
4. **复活失败后果可见**：`ReviveService.TryRevive` 失败时（包括 `IsPermanentlyLost` 阈值），不能只 "ok=false" 沉默返回——必须给玩家看到具体失败文本 + 可能的产出（如"残魂"物品、永久损坏的灵魂石）。

这四条是"死亡-复活"被接入具体技能 / 设施 / UI 时的验收条目；不满足其中任何一条，就认为该次接入**没完成**。

## 灵魂（扩展目标）

> 这是一节**扩展目标**，尚未在代码层实装。现在 `Actor.RevivalCount` / `RevivalCostModel.IsPermanentlyLost` / `ItemCorpseMetadata.SourceActorId` / `soul_fragment` 物品是它的前置雏形。本节定义目标形态，避免以后做着做着偏离。

把"死亡不是终局"扩展到"**身体也不是灵魂的终局**"：灵魂从 `Actor` 里解耦为独立实体，可以跨越身体、跨越世代。这一步服务愿景的"世界连续 + 结果可追溯"在更长时间尺度上的延伸。

### 核心抽象

`Soul` 成为一等对象，承载以下跨身体信息：

- `SoulId`（独立于 Actor/Body）
- `Personality`（10 轴人格偏移，从现在的 `Actor` 搬过来）
- `MemoryLedger`（跨身体的记忆，可衰减不消失；区别于 `ActorMemoryModule` 里"这具眼睛看到的"）
- `SkillImprints`（灵魂层技能烙印；身体换了仍残留一部分）
- `RevivalCount` / `ScarLevel` / `IsPermanentlyLost`（从 `RevivalCostModel` 搬过来）

`Actor` 退化为身体：`Species` / `Gender` / `Age` / `BaseAttributes` + `CurrentSoulId?`（`null` 表示空壳或尸体）。表现行为由 `Soul × Body` 的组合产出。

### 三种跨身体操作

所有操作都落在 `Soul` 这一层，通过 `ServerActionGateway` 下发：

| 操作 | 语义 | 硬代价 | 旁观反应 |
|---|---|---|---|
| **复活** | 原 Soul 装回原 Body（尸体） | 已有：材料 + 多回合仪式 + mood scar + capacity 折损 | 已有：`CasualtyWitnessed` / `witnessed_death` / `ally_died` thought |
| **夺舍** | A 的 Soul 进入 B 的 Body（B 的 Soul 被推出 / 囚禁 / 消灭） | `ScarLevel+1 tier`、身体不适配 thought（-mood 若干回合）、老朋友逐步发现"他不像他了" | 附近 NPC 挂 `personality_changed` thought；`RumorBus` 发 `possession_witnessed` |
| **轮回** | 死后未及时复活 → Soul 进入新生 Body（婴儿 / 野兽 / 路人 NPC） | `MemoryLedger.Fade(0.7)` + 技能烙印衰减到 10-30% + 人格偏移部分保留 | 旧熟人发现时触发"似曾相识"事件 |
| **分身** | 一个 Soul 同时承载多个 Body | 每分身 -8% capacity（灵魂带宽分摊）；`Puppet` 主死全死 / `Avatar` 主死全死分死只扣 `ScarLevel` | 分身间"灵魂同步"有延迟；多人里必走 `ServerActionGateway` |

### 与现有系统的互锁

- **多角色 + 单焦点守不破**：分身再多，一次仍只主动控制一个 Body。
- **RelationshipModule**：关系的"本体"挂 `Soul`（夺舍后老朋友"逐步觉察不对"）；"第一印象"挂 `Body`（夺舍刚完成时认识 Body 的人按旧关系对待，过几回合才被 `personality_changed` thought 驱动走向怀疑）。
- **ActorMemoryModule**：目击事件同时写入**观察者 Soul 的 `MemoryLedger`**（跨世持久）和**观察者 Body 的本地 `ActorMemory`**（这一具眼睛短期记忆）。
- **RumorBus**：新增事件类型 `possession_witnessed` / `reincarnation_suspected`，沿用同一审听模型。
- **死亡仪式感延伸**：焦点切换不限于"队伍下一位成员"，Soul 转世后若玩家选"跟随灵魂"，焦点会缓动到新 Body。

### 明确的非目标（守愿景边界）

- **不做"升天 / 成神 / 末日"收场**——灵魂系统服务"代入感 + 世界连续"，不是 JRPG 终局叙事。
- **分身 ≠ 派系 / 公会**——是"同一个灵魂的多点存在"，不是"多个独立人物组成势力"，和 `PartyModule` / `Factions` 不重叠。
- **NPC 也能被夺舍 / 轮回**——不限玩家队伍；否则"世界连续"会因为只有玩家有灵魂而失效。
- **不做"灵魂全知"**：分身之间、轮回前后的信息同步都要**可观察到的延迟或成本**，否则退化成 MMO 式即时共享。
- **不绕过 `ServerActionGateway`**：多人联机里所有灵魂跨身体操作都走统一入口，客户端不能任意改他人 `Actor.CurrentSoulId`。

### 落地顺序（只作为方向，不作为里程碑）

按"结构解耦 → 最小玩法 → 扩展玩法"的顺序推进，每一步都要独立可回归：

1. **`Soul` 解耦**：把 `RevivalCount` / `Personality` 从 `Actor` 搬进 `Soul`，`Actor.CurrentSoulId` 建立；复活路径改为"Soul 重新绑 Body"。**不加新机制，只重构**——玩家体感不变，为后面开门。
2. **夺舍**（最小的"灵魂跨身体"操作）：一个 skill / item 能让 A 的 Soul 装进 B 的 Body；补 `possession_witnessed` rumor；加 `personality_changed` thought。
3. **轮回**：Soul 死后若 N 回合内未被复活，自动附着到新生婴儿 / 路人 NPC；记忆淡化规则落地。需要 demographics / 婴儿系统的配合。
4. **分身**：先做 `Puppet` 一种（主死全死最简单），`Hivemind` / `Avatar` 后做。

### 验收条件

对应愿景"决策标尺"的核心要求，`Soul` 这节什么时候算"真的落地"：

1. **可追溯性**：玩家能通过 UI 或行为回推"这个 NPC 刚才被夺舍了 / 是某人转世"。不满足时这一节算没做。
2. **连续性**：`Soul` 在存档 / 读档 / 联机 resync / 楼层切换时不丢失 `MemoryLedger` / `ScarLevel`，对齐现有 `SaveModule` 契约。
3. **代价可见**：每次夺舍 / 轮回 / 分身都有玩家能读到的负面后果（thought / HUD 信号 / NPC 反应），不允许无代价通过。
4. **边界守门**：任何实装都必须能回答"这个改动有没有破坏'单人优先 + 等距 2.5D'"。

## 决策标尺

评估一个改动时，按顺序问自己：

0. **（一票否决）这个改动离"最终可玩"更近了吗？**
   ——在当前仍是早期原型阶段，任何不能把"玩家能连续玩下去的最小闭环"向前推进的改动都应延后。
   技术上再优雅、理论上再符合愿景的系统，只要对玩家闭环没贡献，就不是当下该先做的。
   这条是前置闸门；过了它，再看下面 1–4 条。
1. **这个改动让世界更连续了吗？**
   ——例如 NPC 离开视野后行为是否一致、存档恢复后状态是否完整。
2. **这个改动让系统之间更互锁了吗？**
   ——新机制应该与至少一个已有系统（需求/健康/威胁/性格/天气/时间/社交…）产生可观察的因果关系。
3. **这个改动让玩家的操作后果更可追溯了吗？**
   ——玩家应能从后续 UI、日志、NPC 行为或世界状态读出刚才做过什么。
4. **这个改动保护了"单人优先 + 等距 2.5D"的边界吗？**
   ——不为了 MMO 规模或 3D 写实画面牺牲现有表现风格与会话模型。

前三条都不中的改动通常不是这个项目该优先做的；第 4 条是边界守门，不是加分项。
**第 0 条是前置闸门**：无论后四条怎么亮，没过第 0 条就先不做。

## 明确的非目标

- 不追极端写实画面或 AAA 视觉规模；等距 2.5D 的风格化表现足够。
- 不追 MMO 级的并发与社交规模；多人是"小团体共玩一个世界"而不是大区服。
- 不追无脑数值堆砌或简单数值曲线；深度来自系统互锁，不来自膨胀的伤害与等级。
- 不把"故事"写成固定剧本；故事是玩家自己用系统涌现出来的轨迹。
- 不引入 ECS / 通用状态机 / 总线框架来替代现有运行时结构，当前重构路线优先于框架化（见 [`开发约定.md`](./开发约定.md) 与 [`重构路线图.md`](./重构路线图.md)）。

## 什么时候更新这份文档

只有当产品定位、体验目标或非目标发生变化时才更新。
"又想到一个想做的功能"不是更新这份文档的理由，那应该落到具体系统的设计/重构计划里。
