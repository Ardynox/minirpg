# MiniRPG 涌现世界路线图

这份文档只回答一个问题：**在现有 Utility AI 基线之上，怎么让世界开始"自己长故事"？**

不展开 AI 理论教程；只描述 MiniRPG 的下一步目标、现有基线、以及"不要做什么"。其它决策见 [`重构路线图.md`](./重构路线图.md) 与 [`架构现状.md`](./架构现状.md)。

## 目标

从 "NPC 会自己过日子" 推进到 "世界会自己长事件"：玩家 2 小时游戏后会自然说出"因为发生了 X，所以这个区变乱了 / 那人变了"，而不是"NPC 会巡逻会吃饭"。

## 现有基线（第一层已基本到位）

MiniRPG 在"NPC 会自己过日子"这一层已经覆盖约 80%：

- 决策：`UtilityBrain.Evaluate` + `InputResolver`（~60 输入源） + `ResponseCurve`（6 种曲线） + 三层思考缓存（`UtilityCache`）
- 数据驱动：`Data/Config/utility_actions.json`（~27 个 Action 不改代码可调）
- 性格：`Data/Config/personality_defaults.json`（10 轴 + 种族/职业偏移）
- 行为执行：`Executors/` 按行为簇分七类（Need / Combat / Social / Survival / MentalBreak / Job / Idle）
- 感知输入：`AwarenessModule`（4 状态 FSM，只做 AI 输入）、`ThreatDetection.HasNearbyThreat`
- 持续状态：`GameState`、`Actors`、`WorldMap / ChunkData`；`Needs/*`；`thoughts.json`（带 `moodOffset` + `durationTurns` 的情绪痕迹）
- 玩法系统：战斗 / 医疗 / 手术 / 交易 / 种田 / 巢穴 / 心理崩溃

第一层剩下的"更多 Action"按需补即可，属于数据工作，不需要架构动作。

## 缺的四件事（第二层）

要让世界开始"自己长事件"，需要补这四件**小而内聚**的东西。顺序很重要，后一步依赖前一步。

### 第 1 步：`GameEventConsequenceRouter` ✅ 骨架已落地，✅ AI 路径已接通

对称于已有的 `App/RuntimeUi/GameEventPresentationRouter`（后者负责 UI/FX/日志），补一层**系统消费端**：把 NPC 行为产生的 `GameEvent` 分发给治安、关系、经济等系统。

- 落点：`MiniRPG.Shared/Core/Events/GameEventConsequenceRouter.cs`（Shared 里，因为系统层不依赖 Godot）
- 接入：
  - 玩家指令路径：`LocalSessionBackend.AttachConsequenceRouter` → `LocalSessionBackend.SubmitCommandAsync` 在 dispatch 前调用 `DispatchConsequences`。
  - **AI / 时间线路径**：`Main.ApplyTimelineStep` 在 `Dispatch(events)` 之前调用 `_consequenceRouter?.DispatchConsequences(_state, result.Events)`，保证 AI 产出的 combat_attack / actor_killed 事件也回灌社交模块。
- `Main.InitializeCoreServices` 构建 router 并注册 handler；`FinalizeSessionPanels` 统一触发 `Reset()`；同时把三个社交模块实例赋给 `AIDispatcher.Relationships/ActorMemories/Rumors`，`AIBehaviorContext` 才能传给 `InputResolver` 使用。
- 已注册的 handler：`IncidentStatistics`（in-memory 事件计数器）、`RelationshipModule`、`ActorMemoryModule`、`RumorBus`。
- 约束：`GameEvent` 保持唯一事实流；消费端只读 + 触发后续 module 的方法，不要绕过 `ServerActionGateway` 直接改状态。
- 多人路径：服务端 ConsequenceRouter 仍未挂（P0-7，由 `claude-mp-fix` 进程接管）。

### 第 2 步：`RelationshipModule` ✅ 骨架 + ✅ AI 已读取（首版规则待扩）

- 落点：`MiniRPG.Shared/Core/Social/RelationshipModule.cs`（和现有 `SocialModule`"社交动作执行器"平级）。
- 数据：`Dictionary<(observerId, subjectId), RelationshipState>`；`RelationshipState` = `(Trust, Fear, Debt)`。
- 事件规则（首版）：hostile `combat_attack` → 受害者对攻击者 `Fear += HostileAttackFearGain (0.10)`；其它事件随 roadmap 推进添加。
- 已暴露 InputResolver：`RelationshipTrust<target>` / `RelationshipFear<target>`，均做 Clamp01。
- 已被消费：`Data/Config/utility_actions.json` 的 `flee_combat` 末尾加了一条 `RelationshipFear<target>` linear consideration；后续 `chase_enemy` / 守卫 patrol / hostile_disposition 等可按相同模式逐个加。
- 持久化：**仍故意未做**——内存版本，`Reset()` 随 session 切换触发；接 SaveFile 的信号是"玩家 save/load 后 NPC 不记仇"。
- 不要做：不要重做 `PartyModule` / `Factions`，它们回答的是"队伍 / 阵营归属"，关系图补充的是"个体对个体"。
- 下一小步：增加事件规则（gift given / debt repaid / betrayed）——前提是先在玩法层埋出对应的 `GameEvent`（`SocialModule.gift_action` / `TradeModule.debt_settled` / `betrayal` 暂均无）。

### 第 3 步：`ActorMemoryModule` ✅ 骨架 + ✅ AI 已读取 + ✅ actor_killed 旁观者已记忆

- 落点：`MiniRPG.Shared/Core/Social/ActorMemoryModule.cs`
- 数据：`Dictionary<actorId, List<ActorMemory>>`；`ActorMemory` = `(SubjectId, Kind, Strength)`；`Kind` 枚举含 `HostileAttackBy / DebtOwedTo / KindnessReceived / BetrayalBy / CasualtyWitnessed`。
- 容量：`MaxMemoriesPerActor = 32`，FIFO 驱逐。
- 事件规则（当前）：
  - hostile `combat_attack` → 受害者记一条 `HostileAttackBy` memory（`Strength = 0.5`）。
  - `actor_killed` → 同 Z 层 Chebyshev<=8 范围内每个非死者 actor 记一条 `CasualtyWitnessed`（`Strength = 0.4`），subject 是死者。`actor_killed` 暂不带 `InitiatorId`，所以无法记 killer 归因，CombatModule 一旦补 `InitiatorId` 即可加 `KilledBy` 聚合。
- 已暴露 InputResolver：`MemoryFearTowards<target>` / `MemoryDebtOwedTo<target>` / `MemoryBetrayalBy<target>`，三者都走 `SumStrength(observer, subject, kind)` 只读查询。
- 复用：`thoughts.json` 已有 `moodOffset` + `durationTurns` 衰减语义，可复用一半结构；`Thoughts` 关心"我自己的情绪痕迹"，`Memory` 关心"我对 X 的事的认知"——两套存，别混。
- 下一小步：把 `Tick` 衰减接到 `TimelineTurnManager`（已实现 `Tick`，目前由 `Main.TickSimulationSystems` 在 `ApplyTimelineStep` 末尾调用，但缺多人对账）；新增 `gift_given` / `theft` 事件并补 `KindnessReceived` / `DebtRepaid` 规则。

### 第 4 步：信息不对称（`RumorBus`）✅ 骨架 + ✅ AI 已读取 + ✅ actor_killed 已发流言

- 落点：`MiniRPG.Shared/Core/Social/RumorBus.cs`
- 数据：`Rumor = (Id, SubjectId, Kind, Credibility, SourceX/Y/Z, SpreadRadius)`；`RumorKind` 枚举含 `AttackWitnessed / TheftWitnessed / CasualtyReported`。
- 审听模型（首版）：Chebyshev 距离 + 同 Z 层；`QueryAudibleAt(x, y, z)` 返回能听到的 rumor。不存 per-actor `NpcKnowledge`——节省一整块复杂度，代价是目击者和远方听众暂无区分。
- 事件规则（当前）：
  - hostile `combat_attack` → `AttackWitnessed` rumor（subject = 攻击者，source = 受害格）。
  - `actor_killed` → `CasualtyReported` rumor（subject = 死者，source = 死亡格）。
- 已暴露 InputResolver：
  - `NearbyRumorSeverity`：Σ severity_weight × credibility（AttackWitnessed=0.6 / CasualtyReported=1.0 / TheftWitnessed=0.4），Clamp01。
  - `HasRecentTheftRumor`：在范围内听到任意 `TheftWitnessed` 即返 1。
- 下一小步：
  - 引入 `NpcKnowledge` per-actor 字段，让"听到过"与"仍相信"分开，支持记忆淡忘。
  - 补 decay-per-turn 已实现 `RumorBus.Tick`，按 `TimelineTurnManager` 钩子淘汰已接（同 ActorMemory）。
  - 在玩法层埋 `theft` 事件，让 `TheftWitnessed` rumor 真正出现。
- 关键（保持）：**NPC 的 Utility 评分应读 rumor 而非全局真相**——当 `NpcKnowledge` 落地后，这是"信息不对称"的分水岭。
- 不要做：一开始不要给所有 NPC 加 Knowledge；先让目击者、相关阵营成员、巡逻守卫有，其他人默认空。

### 第 1-4 步接线度（2026-04-19 更新）

| 维度 | 现状 | 关键证据 |
| --- | --- | --- |
| AI 事件回灌（路径 1） | ✅ 通 | `Main.ApplyTimelineStep` 已加 `DispatchConsequences` |
| AIDispatcher 注入 | ✅ 通 | `Main.InitializeCoreServices` 三行赋值 |
| InputResolver 暴露 | ✅ 7/7 | 见 `InputResolver.RegisterSocialInputs` 末尾 |
| Utility action 真消费 | ⚠ 1/N | 仅 `flee_combat` 加了 `RelationshipFear<target>` |
| 事件规则覆盖 | ⚠ 2/8 | 已：`combat_attack` × 3 + `actor_killed` × 2；缺：`gift_given` / `debt_repaid` / `theft` 等"事件本身先得有" |
| 持久化 / 多人 | ❌ 未做 | 等 InputResolver 在实战中真消费、且多人服务端 ConsequenceRouter 接通后再做 |

### 可选第 5 步：治安 / 经济的事件反馈

等前四步跑通、且一组"会传播的后果链"上线，再考虑：

- `DistrictSecurityLevel`（按事件增加）→ 影响守卫 AI 的巡逻生成与盘查阈值
- `TradeModule.AdjustPriceOnEvent`（库存减少 / 抢劫 / 封路 → 价格微调）

这两项在前四步没打好底之前做是白做。

## 不要做的事

- **不要先上 GOAP**。`UtilityActionDef` 已经数据驱动，多步行为可以靠"上一个 Action 留下的状态 → 下一个 Action 评分变化"自然串联；GOAP 的 planner / 前置条件 / 回溯搜索会让维护成本飙升，先把状态回写做完再决定是否需要。
- **不要引入 LLM 驱动 NPC 决策**。延迟不可控、成本不可控、复现不可控。LLM 只适合"包装层"（把 `Memory` + `Rumor` 翻译成对白），决策还是走 Utility AI。
- **不要把 `NpcKnowledge` 合进 `GameState` 的全局读面**。每个 NPC 的知识是 per-actor 的，**必须可以和世界真相发生偏差**——否则"信息不对称"失效。
- **不要一次做 100+ 个 NPC**。30 个 NPC + 完整事件闭环 > 300 个 NPC + 没有后果传播。
- **不要把"包装层"和"世界模拟"混在一起**。数据结构只保留结构化字段（`eventKind` / `strength` / `decay`），对白和描述由模板层或后续可选 LLM 翻译。

## 完成判定

不用里程碑文档，用**玩家体感**作为完成标准：

| 阶段 | 判定句式 |
| --- | --- |
| 第 1 步完成 | 玩家能观察到 "A 发生之后 B 反应"（例：偷东西 → 巡逻加强） |
| 第 1-2 步完成 | 玩家会说 "那个人好像记仇" |
| 第 1-3 步完成 | 玩家能复述单个 NPC 的个人小史 |
| 第 1-4 步完成 | 玩家会说 "我误会了那个人" 或 "这个流言传开了" |
| 第 1-5 步完成 | 玩家会说 "这个街区气氛最近变了" |

玩家无法自然说出对应句式时，不算完成。
