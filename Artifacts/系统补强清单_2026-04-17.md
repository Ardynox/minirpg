## A 类：骨架已有，值得加深

### A1. Event/Storyteller：补足 IncidentDef 与 IncidentWorker 密度

- **现状**：`MiniRPG.Shared/Core/Event/Storyteller.cs` 已实现 RimWorld 式调度器（`CheckInterval = 30` 回合、威胁历史、延迟事件队列、权重选择）。`IIncidentWorker` / `IncidentDef` / `StorytellerState` 骨架完整。
- **缺口**：注册到 Storyteller 的具体 IncidentWorker 数量（需要盘点 `StorytellerDefLoader` 加载的 JSON 数量）。"世界自发产生事情"的密度不够，代入感弱。
- **建议切入**：
  - 新建 `Data/Config/incidents.json` 或类似数据文件，按主题分组定义 incident（自然灾害 / 野外遭遇 / NPC 来访 / 瘟疫 / 季节事件 / 小商队）。
  - 每类主题提供至少 2–3 个 IncidentWorker 实现。
  - 每个 IncidentWorker 产出 `GameEvent`，让 `GameEventPresentationRouter` 把它翻成日志 + UI。
- **愿景对应**：**世界连续**（世界自发产事） + **代入感**（故事感来自事件密度）。
- **规模**：**M**（骨架存在，主要是写定义 + worker）。

### A2. Social：补 Opinion 事件化驱动与 Memory/Thought

- **现状**：`SocialModels.cs` 有 `RelationEntry { Opinion, Tags, LastInteractionTurn }` + `SocialState`；`SocialModule.cs` 提供社交互动入口；`SocialInteractionLoader` 负责数据加载。
- **缺口**：Opinion 是静态整数，没有"事件记忆"——没有"A 救了 B → +30 opinion 持续 30 天，然后衰减" 这类 RimWorld/Elin 式 Thought。当前结构很难让玩家感觉"NPC 因为具体事情对我改观"。
- **建议切入**：
  - 新增 `Core/Social/OpinionEventDef`（JSON 驱动：`{ id, baseDelta, durationTurns, decayCurve, stackPolicy }`）与 `OpinionLedger`（按 actor 存一串活跃 event，每回合衰减）。
  - 在 `SocialModule` 提交社交互动时，除修改 opinion，还插入一条 OpinionEvent 到 ledger；opinion 的"当前值"改为 `baseOpinion + Σ(活跃 event)`。
  - 给 `GameEventPresentationRouter` 加一个翻译层，让玩家能在日志里看到"B 记住了 A 救了他"。
- **愿景对应**：**结果可追溯** + **代入感**。
- **规模**：**M**。

### A3. Needs.MentalBreak：补崩溃后续闭环

- **现状**：`MentalBreakModule.cs` 存在，能触发精神崩溃。
- **缺口**：崩溃后"24 小时内留阴影 / 其他 NPC 因旁观受影响 / 康复后给自己 debuff"这种可追溯尾巴，不确定是否完整。
- **建议切入**：
  - 审查 `MentalBreakModule` 当前有没有 break 结束事件、是否有持续 debuff。
  - 若没有，引入"MentalBreakAftermath"概念：持续 N 回合的 opinion/mood debuff，同时给 `OpinionLedger`（见 A2）插入"旁观者 thought"。
- **愿景对应**：**结果可追溯**。
- **规模**：**S**（加深，不大改）。
- **依赖**：和 A2 配合做会更顺。

### A4. Job：补技能熟练度 + 性格驱动的工作偏好

- **现状**：`JobScheduler.cs` + `JobExecutor.cs`。基础任务调度有。
- **缺口**：RimWorld 的"做木工 +1 skill，做快了 / 做精了"未见；`PersonalityModule` 10 轴性格（`diligence`/`patience`…）是否反馈到工作选择与完成时间/品质，也未见显式闭环。
- **建议切入**：
  - 在 `ActorSkillState`（如有）加 `{ skillId, level, experience }`，Job 完成时回写 xp。
  - `JobScheduler` 选任务时读 `personality.diligence / patience`，偏置权重。
  - 完成品生成时读 skill.level，决定 quality（见 B6）。
- **愿景对应**：**结果可追溯**（人工品能看出"是谁做的、那时水平如何"）。
- **规模**：**M**（需要触达多个现有系统）。

### A5. Health.FireSystem → 环境灾害家族

- **现状**：`FireSystem.cs`、`HeatActionModule.cs`、`RoomContextAnalyzer.cs`、`DefaultEnvironmentExposureProvider.cs` 在 Health 目录下，天气有 `fire.json` 配置。
- **缺口**：只有火这一个环境灾害类别，其他灾害（洪水、毒气、辐射、风暴、雷击烧毁建筑）没有统一抽象。
- **建议切入**：
  - 抽 `IEnvironmentHazard` 接口，让 `FireSystem` 成为它的第一个实现。
  - 后续以此添加 `LightningStrikeSystem`、`FloodSystem` 等，每个都是 IncidentWorker 的延伸（见 A1）。
- **愿景对应**：**世界连续** + **结果可追溯**。
- **规模**：**M**（先抽抽象，再新增 1–2 个灾害）。

## B 类：愿景重要但仓库里没有专门系统

### B1. Calendar / Season（季节日历）

- **现状**：有 `DayNightCycle`（日夜循环）和 `Weather`，没有 `Core/Calendar/` 或 `Core/Season/`。当前对"今天几月几日"没有显式概念。
- **缺口**：
  - 玩家没法感受"过完春天了"这种时间标尺。
  - 作物生长、NPC 节日、天气频率都无法按季节区分。
- **建议切入**：
  - 新建 `MiniRPG.Shared/Core/World/Calendar.cs`（或独立 `Core/Calendar/`）：概念为 `{ Year, Season, Day, Hour }`，从 `_state.Turn` 派生。
  - 让 `Weather` / `Farm` / `Event.Storyteller` 读 `CurrentSeason` 做权重差异（冬天概率高寒潮，夏天概率高雷暴）。
  - UI：在 HUD 的时间显示处补季节图标，Trade/Dialog 文案可引用"这个冬天…"之类模板。
- **愿景对应**：**世界连续**（时间感）+ **代入感**。
- **规模**：**M**。
- **依赖**：与 A1、A5 有大量横向耦合，做完杠杆最大。

### B2. Faction（派系）

- **现状**：无 `Core/Faction/`。`RoomRuntimeState.Players` 是多人会话概念，不是 NPC 派系。
- **缺口**：
  - NPC 敌友判定只能基于 actor 个体，无法按"流浪者商队 vs 强盗帮" 这种派系级决策。
  - 交易、任务、战斗关系都缺一层政治抽象。
- **建议切入**：
  - 新建 `Core/Faction/FactionDef`（JSON：`{ id, displayName, baseOpinionTo[factionId], hostilityPolicy }`）。
  - `Actor` 加 `FactionId` 字段（默认 neutral）。
  - 让 `ThreatDetection` / `ActorModule.GetAt` 的敌友判定读 faction 关系表。
  - `TradeModule` / `DialogPool` 后续可以按派系定价、定文案。
- **愿景对应**：**世界连续** + **代入感**。
- **规模**：**L**（一次性改动涉及 Combat / Trade / Dialog / Social 多处读取点）。

### B3. Memory / Thought System（情绪记忆）

- **现状**：`Needs.NeedSystem` 有生理需求，但没有"记忆驱动情绪"系统。心情只看当前需求状态，没有"NPC 因为刚看到同伴死亡难过三天"。
- **缺口**：代入感的支点。玩家做的事必须在 NPC 的情绪上留下可读痕迹。
- **建议切入**：
  - 新建 `Core/Memory/ThoughtDef`（JSON：`{ id, moodDelta, durationTurns, stackLimit, decayCurve, triggers[] }`）。
  - `Core/Memory/MemoryLedger`：每 actor 一串活跃 thought，按 turn 衰减，超过 stackLimit 合并。
  - `GameEvent` 走 `MemoryRouter` 时，按 def 把对应 actor 的 thought 插入 ledger。
  - Mood 总值 = `baseMood(needs) + Σ(活跃 thought)`。影响 `MentalBreakModule` 判定与 Social opinion 增减。
- **愿景对应**：**代入感** + **结果可追溯**（最重要的一块）。
- **规模**：**L**。
- **强烈建议**：在 A2（Social Opinion Ledger）之前做好，A2 可以直接复用 `MemoryLedger` 机制。

### B4. Reputation（玩家在派系内/世界的名声）

- **现状**：无专门系统。只有 Social 的 actor-to-actor opinion。
- **缺口**：
  - 没法表达"玩家偷过某派系的东西 → 整个派系敌视我"。
  - Trade / Quest / 动态 incident 很难按玩家声望做差异化分支。
- **建议切入**：
  - 依赖 B2 Faction；在 `FactionState` 上加 `PlayerReputation`（`int -100 ~ 100`），事件驱动增减。
  - 让 `Storyteller` 挑 incident 时优先选与当前声望"能产生戏剧反差"的。
- **愿景对应**：**世界连续** + **结果可追溯**。
- **规模**：**M**（在 B2 做完之后）。

### B5. Quest / Dynamic Commission

- **现状**：有 `QuestPanel` UI，但没有 `Core/Quest/` 目录，推测 quest 是写死/JSON。
- **缺口**：
  - 无法按玩家状态（声望、派系关系、季节、当前持有物）动态生成任务。
  - 没法让 Storyteller 把 incident 转成"限时委托"。
- **建议切入**：
  - 新建 `Core/Quest/QuestDef` + `Core/Quest/QuestGenerator`（读 IncidentDef + FactionDef + PlayerStats）。
  - `QuestState` 挂在 `GameState` 下，可序列化。
  - 后续接 UI：`QuestPanel` 显示生成的委托，玩家接/拒会反向影响 reputation。
- **愿景对应**：**世界连续** + **结果可追溯**。
- **规模**：**L**（骨架至关重要，细节可迭代）。
- **依赖**：B2 + B4。

### B6. Item Quality / Degradation

- **现状**：物品模型未见 quality / durability。
- **缺口**：
  - 玩家工匠技能再高也看不到差异。
  - "祖传的剑" "我爷爷传下来的锄头"这种代入感点没法做。
- **建议切入**：
  - `Item` 模型加 `Quality { Crude, Normal, Good, Masterwork, Legendary }` 与 `Durability { current, max }`。
  - 建造 / 制作完成时读 actor.skillLevel 映射到 quality。
  - 装备使用 / 天气侵蚀扣 durability，到 0 变成破损需要修复。
- **愿景对应**：**结果可追溯**。
- **规模**：**M**。
- **依赖**：A4（Skill 熟练度）才值得做。

### B7. Crafting / Recipe Graph（工艺网）

- **现状**：有 `Farm`（作物）与 `Facility`（建造），但没有独立的"配方网络"抽象。
- **缺口**：Elin 深度感很大一部分来自"原料→中间件→成品"的层级链。当前只能在各自模块里零散定义。
- **建议切入**：
  - 新建 `Core/Crafting/RecipeDef` + `Core/Crafting/RecipeGraph`，把已有的 Farm 产出、Facility 成品、Cooking（若有）纳入同一图结构。
  - UI：一个可视化 recipe 树 / 配方面板。
- **愿景对应**：**结果可追溯** + **系统互锁**。
- **规模**：**L**。
- **依赖**：B6（quality 让工艺有追求目标）。

## C 类：系统存在但耦合反馈缺失

### C1. Weather × Farm × Mood 反向耦合

- **现状**：Weather / Farm / Needs 三者独立；未确认是否有"下雨 → 作物加速生长 / NPC 心情变化"。
- **缺口**：最常见的"感到世界在活着"信号来自这种跨系统小反馈。
- **建议切入**：找 `FarmModule.Tick` / `NeedSystem.Tick`，补一段按 `CurrentWeather` 读权重的代码。
- **愿景对应**：**系统互锁** + **世界连续**。
- **规模**：**S**（每加一条耦合几十行内）。

### C2. Zone 深度扩充

- **现状**：`Core/Zone/ZoneModule.cs` 只有 2 文件。
- **缺口**：RimWorld 的 Zone 是储藏 / 生长 / 休息 / 禁入多维度，当前只支持非常粗的语义。
- **建议切入**：扩展 `ZoneKind` 枚举 + 每类 zone 的判定函数，`JobScheduler` 按 zone 偏好选任务。
- **愿景对应**：**结果可追溯**（玩家的规划能被 NPC 看懂）。
- **规模**：**M**。
- **依赖**：A4（Job 扩展）。

### C3. Trade 动态化

- **现状**：`TradeModule.cs` + `Core/Trade` 只有 2 文件。贸易估计是静态定价。
- **缺口**：不考虑季节（稀缺）、派系关系（加价）、玩家声望（折扣）。
- **建议切入**：先接 B1 / B2 / B4 的读取，让 `TradeModule.QuotePrice` 按多个 modifier 叠加。
- **愿景对应**：**系统互锁**。
- **规模**：**S–M**（前置做完后加这些读取很快）。

### C4. Dialog 事件反射

- **现状**：`Dialog/DialogRuleEngine.cs` + `TemplateRenderer.cs`，按规则生成对话文案。
- **缺口**：对话里没有"刚才发生过 X 事件"的反射，NPC 不会主动提起玩家最近的事。
- **建议切入**：让 `TemplateRenderer` 能读 `MemoryLedger`（B3）/ `Storyteller` 近期 incident，往模板里填"今早你…"这类变量。
- **愿景对应**：**代入感** + **结果可追溯**。
- **规模**：**S**（一旦 B3 / A1 做好）。

## 推荐优先顺序

按"杠杆率 × 前置依赖"排，建议这样走：

1. **B3 Memory / Thought System（L）** —— 这是其他系统变得"有记忆"的地基，先做。
2. **A2 Social Opinion Ledger（M）** —— 直接复用 B3 的 MemoryLedger。
3. **A3 MentalBreak 后续闭环（S）** —— 同样复用 B3。此时"代入感"已经能感受到。
4. **A1 Storyteller IncidentWorker 密度（M）** —— 让世界开始自发产事，承接 B3 的 thought 输入源。
5. **B1 Calendar / Season（M）** —— 给 A1 和 Weather / Farm 提供时间标尺。
6. **A5 Environment Hazard 家族（M）** —— 补充 A1 的 incident 类型。
7. **B2 Faction（L）** —— 引入第二层政治抽象，后续 Trade / Quest 都靠它。
8. **B4 Reputation（M）** + **C3 Trade 动态化（S–M）** —— B2 的自然延伸。
9. **A4 Job 熟练度 + B6 Item Quality（M + M）** —— 一起做，给"结果可追溯"的第二条主轴。
10. **B7 Crafting Graph（L）** —— 在 B6 之上。
11. **B5 Quest Generator（L）** —— 依赖 B2/B4 完备后再做。
12. **C 类其他（C1/C2/C4）** —— 在相应前置做完后顺手加，都是几十行改动。

**第一个短期突破口**：B3 Memory / Thought System + A2 / A3 三件合起来做，大约 2–3 周能让玩家肉眼感知到"NPC 会因为刚才的事对我改观"——这是最接近 RimWorld 代入感体验的一步。

## 2026-04-17 校准：以"最终可玩"为目的重排 + 纠错

> **触发**：确认当前项目仍是早期原型（玩家还没怎么玩），参考坐标补充了 **僵尸毁灭工程（Project Zomboid）** —— 生活即玩法、硬核生存模拟。
> 由 [`Docs/产品愿景.md::决策标尺`](../Docs/产品愿景.md) 第 0 条"可玩性优先于理想化"作为前置闸门重新评估。

### 对上半部分的事实纠错

二次扫描代码后发现以下条目的"缺口"判断不准确：

| 原条目 | 原判断 | 实际情况 |
| --- | --- | --- |
| B3 Memory / Thought System | "完全缺失" | **基础结构已存在**：`NeedCatalog.Thoughts` 载入 `thoughts.json`、`NeedSystem.ApplyThought` 能插入 thought、`ThoughtDef { MoodOffset, DurationTurns }` 已定义、`HealthCatalog.GetThought` 也提供 health 衍生 thought。真正缺的是**内容密度**（`thoughts.json` 条目数 + 触发点覆盖）与**衰减/堆叠策略**。应重分类为 A 类。 |
| B2 Faction | "完全缺失 `Core/Faction/`" | **已经有基础**：`AI.FactionRelation` 存在，`Actor.Faction` 字段已用于 `HealthActionModule.TryTendOther` 的敌友判定。缺的是独立 `FactionDef`（JSON 配表）+ 派系级关系矩阵 + 对 Trade/Dialog 的读取。应重分类为 A 类。 |
| B7 Crafting Graph | 只写了"无独立配方图" | 需要先查 `FacilityConstructionModule` 是否已经承担部分工艺链；可能只是"没收敛到统一图"而不是"完全没有"。 |

### 新发现的缺口（补入 B 类）

- **B8 Thirst / Hydration 需求** ✅ **已实施（2026-04-17）**
  - **原现状**：`NeedIds` 只有 `Hunger / Rest / Mood`，没有 Thirst。
  - **本轮落地内容**：
    - `NeedIds.Thirst` / `NeedThoughtSources.ThirstStage` / `Drink`；`ItemTags.Hydration`（"解渴"）。
    - `Data/needs.json` 加 `thirst` def（stages: parched / thirsty / dehydrated）。
    - `Data/need_profiles.json` 的 humanoid/beast 两个 profile 加 `thirst` 到 enabledNeeds + decayPerTurn（humanoid 0.16 / beast 0.18，比 hunger 更快）。
    - `Data/thoughts.json` 加 parched/-2、thirsty/-8、dehydrated/-18 三档 stage thought + drank_water/+1 短时 thought。
    - `NeedSystem`：`Sync` 刷新 thirst stage thought；`GetCapacityMultiplier` 对 thirsty/dehydrated 降 `Moving/Manipulation`（dehydrated 额外拖累 `Consciousness`）；`ProjectDialogState` 加 `water` 投影；`EnsureInitialized` 支持从 `DialogNeeds["water"]` 反向恢复。
    - `NeedActionModule.TryConsumeDrink`（inventory + world 两个 overload）+ `IsDrink`；发 `drink_consumed` GameEvent。
    - 玩家侧：`Data/items.json` 加 `water_flask` / `water_bottle_clean`；`MapGenModule.GiveStarterKit` 让玩家出生带 2 个 water_flask；`TimelineTurnManager.TryExecuteEat` 在食物不匹配时 fallback 到 `TryConsumeDrink`（玩家对水壶点"吃"即可喝）。
    - NPC 侧：新 `DrinkWaterExecutor`（仿 `EatFoodExecutor`）+ `ExecutorRegistry` 注册 `drink_water`；`InputResolver` 加 `thirst_urgency` / `drink_available`；`Data/Config/utility_actions.json` 加 `drink_water` action（bonusScore 0.65，比 eat 略高）。

### 以"最终可玩"为目的的优先顺序（覆盖上半部分的推荐顺序）

**口号**：先让游戏**能被玩下去**，再让它**好玩**，再让它**深刻**。

#### 第 1 梯队：生存闭环必需（MVP）

优先级最高，做不完其它就别开始。

1. **B8 Thirst 需求（S）** ✅ 已完成（见本清单 B8 条目）。
2. **B9 Cooking 加工链（M）** ⚠️ 基础设施已存在（见 B9 校准条目），主要缺"玩家开 bill 的 UI"和地图默认灶台。
3. **死亡 / 复活策略** ✅ 已拍板 + 数据层骨架已落地：
   - 设计已补入 [`../Docs/产品愿景.md`](../Docs/产品愿景.md) "玩家控制模型" + "死亡与复活"段。
   - 代码层：`PartyModule.AnyMemberAlive` / `TryPromoteNextLivingMember`、`ItemCorpseMetadata.SourceActorId`、`Core/Revival/ReviveService`（骨架，带 TODO 注释）。
   - 未做：UI 接入（切换焦点的呈现动画、复活技能/设施的触发器、复活代价配置 JSON），全留给后续批次——Main/Panel 层稳定后再做。

#### 第 2 梯队：让世界有"自己发生事"

1. **A1 Storyteller IncidentWorker 密度（M）** —— 只有一两个 incident 密度太低。目标是每游戏小时触发 1–3 次可识别事件。
2. **B1 Calendar / Season（M）** —— 给 A1 和 Weather/Farm 提供时间标尺。季节影响作物、incident 权重、NPC 行为。
3. **A5 Environment Hazard 家族（M）** —— 抽 `IEnvironmentHazard`，补 1–2 个新灾害（寒潮、雷击）。

这三件合起来做，玩家就能感觉到**"不做什么，世界也有事发生"**。

#### 第 3 梯队：代入感深化

1. **A-revised Thought 内容密度 + MemoryLedger 衰减（M）** —— 在既有 `ThoughtDef` 基础上扩充 thought 条目 + 给每个 actor 加显式 ledger（当前像是通过 Needs 状态隐式管理）。

3. **A3 MentalBreak 后续闭环（S）** —— 崩溃结束后留 thought 痕迹、旁观 NPC 被触发。
4. **A4 Job 熟练度 + B6 Item Quality（M + M）** —— 让玩家的"反复劳动"有成长反馈。

3. **C3 Trade 动态化（S–M）** —— 季节/派系/声望叠加定价。

这是最短路径的"让游戏更像游戏"的一步，风险最低、反馈最直接。
