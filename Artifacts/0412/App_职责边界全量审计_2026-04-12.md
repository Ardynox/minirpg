# App 层职责边界全量审计（2026-04-12）

## 1. 审计范围

- 范围：`App/**/*.cs`，包含 `App/RuntimeUi/*` 与 `App/ResourceCatalogEditor.cs`
- 样本：43 个 `.cs` 文件，按统一签名扫描约 598 个方法入口
- 目标：判断 `App` 层函数是否仍处在“Godot 入口 / 应用编排 / UI 协调 / 适配桥接”的职责边界内，而不是重新滑回领域规则、基础设施细节或单类过载

说明：

- 方法数采用与既有审计文档一致的“签名扫描”口径，便于横向比较
- 对大文件额外做了人工通读，因此结论不只依赖数量

## 2. 判定标准

### 2.1 App 层允许承担的职责

- Godot 场景入口、生命周期、节点装配、事件订阅
- 输入翻译：把键鼠/命令字符串转成应用动作
- 会话编排：开始游戏、继续游戏、切世界、进入编辑器、多人连接
- UI 协调：面板可见性、焦点、HUD 刷新、弹窗切换、日志与特效呈现
- 适配与桥接：把 `Core/Module` 的结果转成 UI 侧副作用

### 2.2 不应继续堆在 App 层的职责

- 直接承载大块领域判定，尤其是“规则选择 + 状态写入”一起做
- 为了解决视图问题而直接改写领域状态
- 同一类同时承担 UI、文件系统、验证、导入、持久化、预览等多种一等职责
- 已完成迁移后仍保留重复 view-model/helper，形成双份来源

### 2.3 评级

- `A`：在职责边界内，职责单一
- `B`：在职责边界内，但已经偏重，继续扩展会很脆
- `C`：函数级边界漂移，文件整体未失控，但已有明确坏味道
- `D`：明显超出单类职责，已构成维护热点

## 3. 总结结论

- 当前 `App` 层整体是健康的，而且比上一轮更清楚。`Main` 已经继续拆出 `GameplayInput / SessionFlow / Startup / Targeting / UiMode / Wiring` 等 partial，入口类的职责面开始明显收口。
- `RuntimeUi` 目录已经形成比较稳定的结构：输入、启动、事件呈现、视图刷新、多人连接、多人运行时、天气实验室、调试面板都各自有独立 coordinator/controller。
- 当前最明显的问题不再是“所有逻辑都在 Main 里”，而是少数热点仍然偏胖。

当前最值得优先盯住的 6 个点：

1. `App/ResourceCatalogEditor.cs` 仍是明确的 `D` 级单类过载。
2. `App/Main.Command.cs::OnCommand` 仍是一张大型命令路由表。
3. `App/Main.Settings.cs::RefreshLocalizedUi` 仍是全局 UI 重刷中枢。
4. `App/Main.MapAndCamera.cs::SyncViewToActiveActor` 仍通过改写 `_state.PlayerX/Y/Z` 来驱动视图，是最明确的函数级边界漂移。
5. `App/RuntimeUi/MainAppFlowCoordinator.cs` 已比旧 `Main` 好很多，但仍同时承载 `SessionFlow + WorldManagerFlow + PreparedLoadFlow + ConfirmFlow` 四组子流程。
6. `App/Main.Startup.cs` 现在成了新的启动装配中心，`InitializePanelsAndChrome` 与 `InitializeCoordinators` 的扇出已经不小。

## 5. 需要单独点名的函数

### 5.1 明确的函数级边界漂移

- `App/Main.MapAndCamera.cs::SyncViewToActiveActor`
  - 目的只是“让镜头跟随当前激活角色”。
  - 但实现方式是直接改写 `_state.PlayerX/_state.PlayerY/_state.PlayerZ`。
  - 这会把视图同步问题转成领域状态写入，属于当前 App 层最明确的函数级边界问题。

### 5.2 仍在边界内，但已经偏重的函数

- `App/Main.Command.cs::OnCommand`
  - 同时处理死亡态返回、模式门禁、多人限制提示、快捷命令分发、文本命令分发。
  - 还没越界，但已经是“不断加 case 就会持续变差”的典型中心函数。
- `App/Main.Startup.cs::InitializePanelsAndChrome`、`App/Main.Startup.cs::InitializeCoordinators`
  - 都还在 App 层边界内，因为它们本质就是运行时装配。
  - 但它们现在已经承载了大量节点绑定、模块构造、依赖连线，后续继续增长时要警惕再次形成“大型初始化函数”。
- `App/Main.Settings.cs::RefreshLocalizedUi`
  - 一次性触达菜单、多人生面板、世界管理、HUD、面板刷新、日志与地图刷新。
  - 这类函数短期有效，长期会让每个新 UI 模块都必须回到这里接线。
- `App/Main.Skill.cs::TryCastArmedSkillAtWorldCell`
  - 同时做目标类型解析、识别技能特殊分支、攻击技能肢体面板决策、施法动作提交。
  - 仍属于应用协调，但已经吸收一部分技能目标策略。
- `App/RuntimeUi/MainAppFlowCoordinator.cs::CommitPreparedLoadAsync`
  - 负责 busy stage、会话切换、prepared load 提交、成功/失败收尾。
  - 边界没跑偏，但它说明 `PreparedLoadFlow` 已经值得单独拆出。

### 5.3 类内职责过载而不是单函数错误

- `App/ResourceCatalogEditor.cs`
  - `BindNodes/BuildFileDialogs/WireEvents` 是视图初始化
  - `RefreshUi/RefreshPreview/RefreshFrameList` 是视图刷新
  - `BuildSliceCandidates/RefreshSlicePanel` 是切片规划
  - `ImportImage/ImportFolder/TryConvertToResPath/ListDirectPngFiles` 是导入与文件系统适配
  - `ValidateEntry/CollectCatalogValidationErrors` 是验证服务
  - `SaveCatalog` 是持久化
  - 单个函数大多还能解释，但把这些职责长期放在一个类里已经明显不合适

## 6. 相比旧版已经改善的点

- `Main` 进一步拆出了 `Main.GameplayInput.cs`、`Main.SessionFlow.cs`、`Main.Startup.cs`、`Main.Targeting.cs`、`Main.UiMode.cs`、`Main.Wiring.cs`，说明入口类正在从“逻辑容器”向“组合根 + partial 分区”演进。
- `Main.Multiplayer.cs` 里的重复房间 view-model helper 已经不见了，`MultiplayerHubCoordinator` 现在是唯一的房间标签/选项构造点。
- `Main.cs` 现在基本只保留生命周期壳层，启动与 wiring 已经被抽走，边界比我最初扫描时更清楚。

## 7. 建议的后续重构顺序

1. 先处理 `ResourceCatalogEditor`
   - 这是独立工具，收益最高，也不会牵动主运行时。
   - 最少拆成 `Controller / PreviewService / SlicePlanner / ImportService / ValidationService`。
2. 把 `OnCommand` 改成表驱动路由
   - 可按 `系统命令 / gameplay 命令 / modal 策略` 三层拆开。
3. 给视图引入独立 camera/view anchor
   - 用视图层状态替代 `SyncViewToActiveActor` 对 `_state.PlayerX/Y/Z` 的写入。
4. 继续横切拆 `MainAppFlowCoordinator`
   - 下一步最适合拆成 `SessionFlowCoordinator` 与 `PreparedLoadCoordinator`。
5. 拆 `RefreshLocalizedUi`
   - 把“永久模块刷新”“可见面板刷新”“HUD/渲染刷新”拆成三个注册点，避免继续扩大扇出。

## 8. 最终判断

- 如果问题是“App 层现在是不是又失控了”，答案是否定的。
- 如果问题是“是否所有函数都已经非常理想”，答案也不是。
- 当前状态更准确的描述是：
  - 绝大多数 App 函数仍在职责边界内
  - `RuntimeUi` 目录已经形成有效收口
  - 风险已经收缩到少数明确热点，而不是全层普遍越界

所以接下来最值钱的工作不是再做一轮大迁移，而是继续做三件事：

1. 拆掉工具型超载类
2. 收口几个高扇出中心函数
3. 清理剩余的函数级边界漂移点
