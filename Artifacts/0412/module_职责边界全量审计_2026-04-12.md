# Module 职责边界全量审计（2026-04-12）

## 范围

- `Module/**/*.cs`
- `MiniRPG.Shared/Module/*.cs`
- 不含 `App/*`、`MiniRPG.Shared/Core/*`、测试项目

## 判定口径

- `职责内`
  - 函数只做本模块应承担的编排、UI 刷新、渲染、适配、存储或工具职责。
- `临界`
  - 函数仍服务当前模块目标，但已经开始夹带另一个 owner 的实现细节，后续继续扩张就会越界。
- `越界`
  - 函数直接修改别的子域状态、嵌入本不属于当前模块的规则决策，或者把本应拆开的第二职责长期固化在当前类里。

补充说明：

- 本文按“文件主职责 + 关键函数组”做全覆盖。
- 未单独点名的构造函数、节点绑定函数、`Open/Close/Refresh`、纯格式化 helper、纯渲染 helper，默认按所属文件主职责计入 `职责内`。
- 如果某个类本身没有明显跨层越界，但单类已经过宽，本文会标为 `临界`，表示“层边界没错，类边界已经太胖”。

## 总体结论

- `MiniRPG.Shared/Module` 已经明显比之前更像应用层：`ContinueStateService`、`WorldCatalogService`、`ReservationService`、`TimelineTurnGateway` 都在收边界。
- 当前最需要继续拆的热点仍然是 `GameSessionModule`、`ServerActionGateway`、`TileMapRenderModule`、`IsometricVoxelRenderer`、`AutoTestModule`。
- 明确越界最重的不是渲染层，而是几处 UI 编排层：
  - `DialogUIModule.ApplyEffects`
  - `CombatUIModule.HandleActorKilled`
  - `TradeUIModule.OnTradeAction`
  - `InventoryPanelModule.TryEquip/TryDrop/TryUse`
- `TileMapRenderModule` 与 `IsometricVoxelRenderer` 暂时没有明显跨层错误，但都已经把“渲染组合”“资源解析”“性能记录”“模式切换”“贴图生成”揉进一个类，属于类边界过宽。

## 优先重构顺序

1. 先拆 `DialogUIModule`、`CombatUIModule`、`TradeUIModule`、`InventoryPanelModule` 的执行职责，让 UI 只负责发命令与展示结果。
2. 再拆 `ServerActionGateway` 的 chest/trade/combat handler，把网关收回“路由 + 参数校验 + 结果汇总”。
3. 然后继续瘦 `GameSessionModule`，把楼层切换、世界初始化、存储路径、storyteller worker 注册拆走。
4. 最后处理 `TileMapRenderModule` / `IsometricVoxelRenderer` / `AutoTestModule` 这种“层边界正确但类边界太宽”的热点。

## 热点深审

### 1. `MiniRPG.Shared/Module/GameSessionModule.cs`

| 函数组 | 判定 | 结论 |
| --- | --- | --- |
| `CreateWorld`、`ListWorlds`、`ListWorldCharacters`、`TryContinue`、`TryLoadGame`、`ResolveContinueTarget`、`BuildContinueButtonText`、`DescribeCurrentSessionLabel` | 职责内 | 这些函数都在做会话入口、目录入口和 continue 编排，是应用层 owner。 |
| `NewGame`、`StartWorldCharacter`、`NewBlankEditorMap`、`LoadGame`、`PrepareLoad*`、`CommitPreparedLoad`、`ApplyMultiplayerRoomSnapshot`、`SaveGame`、`FinalizeLoadedGame` | 临界 | 仍是会话编排主线，但已经同时承担世界初始化、状态修补、本地持久化、多人快照适配。 |
| `ListLegacySaveEntries`、`BuildSummary`、`DescribeSavePath`、`ResolveSavePath`、`BuildSaveHeaderContext`、`BuildPresetScenarioJson`、`ExportPresetScenario` | 临界 | 会话模块已经开始夹带文件系统、摘要文案、preset 导出这些第二职责。 |
| `TryUseStairs`、`ChangeFloor` | 越界 | 这是玩法/楼层迁移逻辑，不该长期放在会话管理器里。 |
| `InitializeWorld`、`EnsureStorytellerWorkers` | 越界 | 一个是世界生成与出生点初始化，一个是 storyteller worker 注册，都更像启动或世界 bootstrap。 |
| `ResolveUserDataDir`、`RewriteSnapshotForPlayer` | 越界 | 前者是存储基础设施，后者是多人快照改写适配，都不是会话模块核心职责。 |

结论：`GameSessionModule` 现在已经比旧版收敛，但仍然是“会话编排 + 世界初始化 + 楼层切换 + 存储路径 + 快照修补”的混合体，仍是第一拆分热点。

### 2. `MiniRPG.Shared/Module/ServerActionGateway.cs`

| 函数组 | 判定 | 结论 |
| --- | --- | --- |
| `Execute`、`ExecuteTimelineAction` | 职责内 | 统一入口和 timeline action 路由正是网关职责。 |
| `ExecuteInteraction`、`ExecuteOpenModal`、`ExecuteCloseModal`、`ExecuteDelegateActor`、`ExecuteReclaimPrimaryActor`、`ExecuteAssignPrimaryActor`、`ExecuteKickPlayer` | 临界 | 仍属于命令执行入口，但已经开始夹带多人 reservation/ownership 的具体细节。 |
| `ExecuteChestTake`、`ExecuteChestTakeAll`、`ExecuteChestPut` | 越界 | 容器取放、库存变更、落地持久化细节都写在网关里，应该拆成 container handler/service。 |
| `ExecuteTradeBuy`、`ExecuteTradeSell` | 越界 | 交易校验、买卖调用、日志拼接都已经是独立交易 handler 的职责。 |
| `ExecuteStartCombat`、`ExecuteEndTurn`、`ExecuteCombatAttack`、`ExecuteUseSkill`、`ExecuteEndCombat` | 越界 | 这些函数已经嵌入 combat mode 规则与 turn gate，不该继续堆在统一网关里。 |
| `ResolveContainer`、`ResolveInventoryContainer`、`PersistContainer`、`ToTradeGoodSource` | 越界 | 这是被 gateway 绑住的实现细节 helper，拆 handler 时应一起迁出。 |

结论：`ServerActionGateway` 的层边界还对，但实现边界已经明显超载，下一步应该按容器、交易、战斗、多人控制权拆 handler。

### 5. `Module/AutoTestModule.cs`

| 函数组 | 判定 | 结论 |
| --- | --- | --- |

结论：`AutoTestModule` 的问题不是层错，而是“总编排器”吞掉了 benchmark、save hack、probe helper，类边界已经明显过宽。

### 6. `Module/DialogUIModule.cs`

| 函数组 | 判定 | 结论 |
| --- | --- | --- |
| `CloseDialog`、`RefreshCurrentEntry`、`RenderEntry` | 职责内 | 都是 UI 流程和展示职责。 |
| `OpenDialog`、`ShowEntry`、`OnOptionSelected` | 临界 | 仍在做对话流程编排，但已直接碰到对话上下文与 NPC 状态。 |
| `ApplyEffects` | 越界 | 该函数直接修改 affinity、mood、memory、gold，并同步 health/need，是明确的领域副作用执行器，不该留在 UI 模块。 |

结论：`DialogUIModule` 应保留“选项切换、面板展示、焦点管理”，把 effect 应用迁到 dialog action/service。

### 7. `Module/TradeUIModule.cs`

| 函数组 | 判定 | 结论 |
| --- | --- | --- |
| `OpenTradeMenu`、`CloseTrade`、`Refresh` | 职责内 | 交易 UI 编排和面板同步是本职。 |
| `OnTradeAction` | 越界 | 该函数已经在 UI 层构建命令、走 client fallback、直接调用 `ServerActionGateway.Execute`，等于把“执行器”留在 UI。 |

结论：交易 UI 应只产生 buy/sell intent，由独立 dispatcher/application service 负责执行并回填结果。

### 8. `Module/Panel/InventoryPanelModule.cs`

| 函数组 | 判定 | 结论 |
| --- | --- | --- |
| 过滤、排序、行渲染、详情渲染、secondary filter、context menu 展示相关函数 | 职责内 | 都属于 inventory panel 的 UI 职责。 |
| `TryEquip`、`TryDrop`、`TryUse` | 临界 | 作为 UI 输入适配还说得通，但已经直接构建命令、提交 timeline action、记录特殊业务日志。 |
| `ApplyServerActionResult` | 越界 | 结果分发与日志回写不该藏在具体 panel 里。 |

结论：`InventoryPanelModule` 现在是“展示 + 命令生成 + 本地 fallback 执行”的混合体，最好抽出 inventory command dispatcher。

### 9. `Module/CombatUIModule.cs`

| 函数组 | 判定 | 结论 |
| --- | --- | --- |
| `HandleActorKilled` | 越界 | 函数名是 UI presentation，但内部既记日志又触发 loot/reward 结算，已经同时承担了战斗事件处理。 |

结论：击杀奖励和掉落应进入 combat event handler 或 loot pipeline，UI 只负责展示产出的结果。
