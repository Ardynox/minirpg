## 一、可玩闭环阻塞（CRITICAL，必修）

### 1. ★ 死亡-切焦点链路完全没接，全队"队长一死即终局"

- **现状**：`MiniRPG.Shared/Module/Session/ActiveActorDeathHandler.cs` 已写好（4-17 完成），但**全仓没人调用**。死亡仍走 `App/Main.Timeline.cs:447-478` 的 `HandlePlayerDeath` 直接 `PlayerDead = true`、写"主菜单"日志。
- **后果**：违反《产品愿景》"焦点角色死亡 → 自动切焦点；全队死亡才永久死"硬要求。当前队伍系统形同虚设。
- **修复方向**：在 `actor_killed` / `actor_incapacitated` 事件路径上调用 `ActiveActorDeathHandler.Handle`，仅当 `AllMembersDead` 才让 `HandlePlayerDeath` 进入终局；其余情况发 `active_actor_switched` 事件，由表现层切焦点。

### 2. ★ "焦点 ≠ PlayerId"在 HUD / 输入 / 表现层全面错位

- **多路验证**：
  - HUD：`App/Main.cs:313-314` `_needsHud.Update(ActorModule.GetPlayer(...))`
  - 命令：`App/RuntimeUi/GameplayCommandCoordinator.cs:55-140` 的 `GetPlayer`
  - 多人预测：`App/RuntimeUi/MultiplayerRuntimeCoordinator.cs:139-147` `TrySubmitPredictedMove`
  - 表现：`App/RuntimeUi/GameEventPresentationRouter.cs:95-122` `e.TargetId == _state.PlayerId`
  - 日志：`Module/LogModule.cs:126-129` 仅 PlayerId 才打印
  - 死亡结算：`App/Main.Timeline.cs:473-475` 用 `ActorModule.GetPlayer` 算金币
- **后果**：Tab 切焦点后需求条仍显示队长、命令路由发给错的人、焦点队员的饥渴日志被静默、多人预测发送错误的 actor。等于队伍系统几乎不可用。
- **修复方向**：抽 `GetActiveActor(state)` 为统一访问点，把上述读路径全部对齐；`PlayerX/Y/Z` 显式降级为"客户端预测/相机锚点缓存"并在《多人联机契约》写明。

### 3. 复活流程 + RevivalCostModel 完全没串起来

- `MiniRPG.Shared/Core/Revival/ReviveService.cs:21-26, 57-111` 的 `TryRevive`：**瞬时**成功，无 HP/肢体恢复、无材料消耗、无回合时长、未调用 `RevivalCostModel`、未触发 `IsPermanentlyLost`。
- `MiniRPG.Shared/Core/Revival/RevivalCostModel.cs` 全仓**无业务调用点**。
- 复活 thought id `revived_memory` / `revived_ally` 在 `Data/thoughts.json` **不存在**，UI 会显示 raw key。
- 注释里说将来读 `Data/revival_costs.json`，**仓库无此文件**。
- **后果**：违反《产品愿景》"复活必有代价 + 仪式感四条验收"；当前等于"任意复活+无副作用"。
- **修复方向**：让 `TryRevive` 必经 `RevivalCostModel`，失败发可本地化 `GameEvent`；接 `TimelineTurnGateway` 让设施/施法回合化；补 thoughts catalog 与 `revival_costs.json`。

### 4. ★ Climb 联机命令反序列化漏分支

- `ClientCommandKind.Climb` / `ClimbClientCommand` 已在协议层定义，但 `MiniRPG.Shared/Core/Multiplayer/ProtocolSerializer.cs:39-74` 的 `DeserializeCommand` switch 无 `Climb` 分支，落 `_ => null`，等同"反序列化失败"。
- **修复方向**：补分支；同时给枚举加"穷尽 switch 单测"防回归（也覆盖未来新枚举值）。

### 5. ★ 联机入口可被脏 JSON 杀进程

- `MiniRPG.Shared/Core/Multiplayer/ProtocolSerializer.cs:29-105`、`MiniRPG.Shared/Module/Network/ENetGameServer.cs:97-118` 的 `JsonDocument.Parse` / `JsonSerializer.Deserialize` 没有 try/catch，异常沿 `Poll → HandleEvent` 冒泡到 `_Process`。
- **后果**：恶意/截断包就能让客户端或服务端进程崩溃。
- **修复方向**：传输入口统一捕获，映射 `ErrorCode.DeserializationError` 或拒绝连接。

## 二、契约违反（HIGH，影响一致性与可重现性）

### 6. ★ 读档 / 继续 / 快载成功路径不调用 `FinalizeSessionPanels`

- `App/RuntimeUi/MainAppFlowCoordinator.cs` 的 `HandleMenuContinue`（279-290）、`RequestWorldManagerLoad`（780-787）、`HandleQuickLoadRequested`（535-544）只 `PrepareSessionTransition + _doEnterGame`，跳过文档要求的"表现层 + 面板层收口"；只有 `FinalizeNewGameStart`（843-846）走全量。
- **后果**：违反《会话生命周期.md》三层清理契约，自动寻路 / 技能栏 / 库存 / 社交缓存等可能残留旧会话状态。
- **修复方向**：所有 `CommitPreparedLoad` 成功且即将进入游玩的分支统一走 `_finalizeSessionPanels(...)`。

### 7. `ChangeFloor` / `TryUseStairs` 几乎不执行清理契约

- 文档把"楼层切换"列为四个会话清理时机之一，但 `MiniRPG.Shared/Module/GameSessionModule.cs:560-594` 只改 `PlayerZ` + `UpdateLoadedChunks`，**不**跑 `_state.Reset`、`_fogTracker.Clear`、`TimelineTurnManager.Reset`、`PartyModule.Initialize`、`ActorDerivedStateUpdater.SyncAllActorsForSession`。
- **后果**：要么楼层切换确实是增量（那文档错），要么就有一组隐性 bug（衍生状态 / 时间线 / 雾不一致）。
- **修复方向**：确定语义后**两边同步** —— 文档改成"楼层切换为增量、不全量 Reset"，或代码补齐契约项。

### 8. `_fogTracker.Clear()` 在读档路径缺席

- 仅在 `NewGame`（96）/ `StartWorldCharacter`（221）/ `NewBlankEditorMap`（254）调用；`FinalizeLoadedGame`（794-821）没清雾。读档后旧雾是否合法没人证明。
- **修复方向**：在 `ApplySnapshot` 后补一次 Clear，或在文档中说明"快照应用即等价 Clear"。

### 9. ★ `ClientCommandRouter` 文档级"统一入口"实际从未实例化

- `Docs/多人联机契约.md` 把它写成单一路由入口；但 grep 全仓**没有 `new ClientCommandRouter(`**。`App/Main.Timeline.cs:157-176` 的 `TrySubmitClientCommand` 和 `App/RuntimeUi/MultiplayerRuntimeCoordinator.cs:198-206` 仍直接走双轨。
- **修复方向**：要么把所有命令提交都收敛到 `ClientCommandRouter.Submit`，要么把文档改成"路由由 `Main` + Coordinator 共同决策"。两者择其一，不能保留漂移。

### 10. RuntimeUi / 编辑协调器直接写 `GameState`，绕过网关

- `App/RuntimeUi/DebugPanelController.cs:149-152`：直接翻转 `_state.RuntimeFreeBuild`。

### 11. ★ `ServerActionGateway` 仍含大量领域规则

## 三、代码硬伤（HIGH，运行时风险）

### 12. 主线程上同步阻塞 `SubmitCommandAsync`

- `App/RuntimeUi/ClientCommandRouter.cs:54-62`、`App/Main.Timeline.cs:168-176` 用 `GetAwaiter().GetResult()` 同步等异步命令。
- **后果**：若后端续约依赖主线程或互锁，会卡 UI 帧。
- **修复方向**：传播 `async Task` 或下一帧消费结果。

### 13. 大量 `async void` 信号处理器无 try/catch
